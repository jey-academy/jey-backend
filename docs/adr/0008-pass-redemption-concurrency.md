# ADR-0008: 패스 중복 사용은 낙관적 락과 유니크 키로 막고, 분산 락은 쓰지 않는다

- 상태: 채택
- 날짜: 2026-10-18

## 배경
동탄고 패스는 한 번만 쓸 수 있다. 데스크 두 곳에서 같은 패스를 동시에 사용 처리하거나 버튼을 두 번 누르면 할인이 두 번 적용될 수 있다.

사용 처리는 한 트랜잭션에서 패스를 "사용됨"으로 바꾸고 사용 기록을 넣는다. 사용 기록에는 유니크 키가 둘 있다(패스 하나에 하나, 학생 한 명에 하나).
구현 중 동시성 테스트에서 같은 패스를 동시에 쓰면 데드락(500)이 나는 것을 발견했다. 사용 기록 INSERT의 외래 키 확인이 패스 행에 공유 잠금을 걸고,
ORM이 INSERT를 UPDATE보다 먼저 보내 두 요청이 서로의 공유 잠금을 기다렸다. 패스 UPDATE를 먼저 보내도록 고쳤다.

설계 때 중복 사용 방지 방식을 비교 실험으로 고르기로 했다. 같은 HTTP 부하를 걸어 정확성과 응답 시간을 쟀다.

## 선택지
모두 사용 기록의 두 유니크 키와 패스의 버전은 그대로 둔다. 다른 것은 패스를 읽는 법, 저장 순서, 트랜잭션 밖의 잠금이다.

1. **낙관적 락(지금)**: 패스를 잠그지 않고 읽고, 패스를 먼저 고친 뒤(버전 확인) 기록을 넣는다. 같은 패스의 경합은 버전 충돌로, 같은 학생의 경합은 유니크 키로 끝나고, 지금 상태를 다시 읽어 409로 답한다
2. **비관적 락**: 패스를 `SELECT … FOR UPDATE`로 읽어 같은 패스의 요청을 줄 세운다. 저장 순서는 1과 같다
3. **기록 먼저**: 잠그지 않고 읽고, 기록을 먼저 넣은 뒤 패스를 고친다(같은 패스는 유니크 키가 먼저 막는다)
4. **Redis 분산 락 + 1**: 트랜잭션 밖에서 패스마다 Redis 락(SET NX + 요청마다 다른 토큰, 내 토큰일 때만 해제)을 잡는다. 못 잡으면 기다리지 않고 409(다시 시도)

## 측정

- 도구: k6. 실제 서버에 HTTP로(로그인, CSRF, 멱등 키, 보안 필터를 모두 거쳐) 부하를 건다. 응답 시간은 사용 처리 요청만 잰다
- 환경: 데스크톱 PC 한 대(14코어, 메모리 32GB)에서 서버, MySQL 8.4·Redis 7.4(컨테이너), k6를 함께 실행. DB 연결 풀 10, Tomcat 기본 설정
- 시나리오(각 300회 반복, 반복마다 새 패스·학생)
  - 경합 N8: 한 패스에 사용 처리 8개를 동시에(가상 사용자 10)
  - 경합 N32: 한 패스에 32개를 동시에(가상 사용자 4)
  - 분산: 서로 다른 패스에 1개씩(가상 사용자 32) — 경합 없음
  - 섞임: 사용 처리 4개와 같은 패스의 링크 새로 만들기 4개를 동시에(가상 사용자 10)
- 판정(하나라도 어기면 그 실행은 실패): 반복마다 사용 처리 성공이 정확히 1개(섞임은 많아야 1개), 진 사용 처리의 답은 예상한 409(이미 사용됨, 신규 아님, 다시 시도)뿐, 사용 처리·링크 새로 만들기 모두 5xx·예상 밖 4xx·연결 실패 0
- 1·2·4번은 시나리오 넷을 3회씩(회마다 서버를 새로 띄움), 3번은 1회 쟀다. 응답 시간은 3회의 중앙값이다

| 방식 | 판정 | 경합 N8 p99 | 경합 N32 p99 | 분산 p99 | 섞임 p99 | 섞임에서 사용 처리 성공 | 진 사용 처리가 받는 답 |
|---|---|---|---|---|---|---|---|
| 1 낙관적 락 | 12/12 통과 | 494ms (459~532) | 424ms (331~668) | 207ms (207~327) | 345ms (300~500) | 188/300 | 이미 사용됨, 링크와 겹치면 다시 시도 |
| 2 비관적 락 | 12/12 통과 | 477ms (467~1514) | 404ms (377~660) | 188ms (175~217) | 331ms (269~1931) | 300/300 | 이미 사용됨 |
| 3 기록 먼저 | 4개 중 3개 실패: 500이 경합 N8 219건, N32 118건, 섞임 475건(+ 링크 5건), 모두 데드락 | 576ms | 291ms | 188ms | 297ms | 161/300 | 대부분 이미 사용됨, 일부 500 |
| 4 Redis 락 + 1 | 12/12 통과 | 399ms (373~472) | 306ms (286~348) | 158ms (139~176) | 313ms (240~337) | 71/300 | 대부분 다시 시도(N32에서 9098/9300) |

괄호는 3회의 최소~최대다.

- 1·2·4번은 36회 모두 중복 사용이 없었다(반복마다 성공 응답이 정해진 수였다). 서버 로그의 오류도 0줄이었다. 3번의 500은 서버 로그에서 모두 `Deadlock found when trying to get lock`이었다.
- 같은 방식·같은 시나리오의 p99가 회차마다 크게 흔들렸다(예: 1번 경합 N32 331~668ms, 2번 섞임 269~1931ms). 1·2·4번 중앙값의 차이(시나리오마다 14~118ms)는 이 흔들림 안이다.
- 4번은 중앙값이 네 시나리오 모두 가장 짧았지만, 경합이 없는 분산(Redis 왕복이 하나 더 있어 더 빠를 까닭이 없다)에서도 가장 짧았다. 회차 안의 실행 순서(늘 마지막)나 환경의 흐름이 섞였을 가능성이 커, 방식의 효과로 가르지 못했다. 경합 시나리오에서 DB 연결을 기다린 요청이 조금 적었던 것(경합 N8 대기 최대 63~67 대 70~78)은 앞단에서 거르는 효과로 설명된다.
- 처음 측정에서는 경합 N32를 가상 사용자 10(동시 연결 320)으로 돌렸다가 일부 연결이 거절되어(접속 대기열이 넘친 것으로 추정) 방식과 무관한 실패가 섞였다. 연결 실패를 따로 세고 동시 연결을 128로 줄였다.

## 결정
1번(낙관적 락 + 유니크 키, 패스를 먼저 고치고 기록을 나중에 넣는다)을 유지한다. 분산 락은 쓰지 않는다.

- 측정 전에 기준을 정했다: 정확성 → 응답 시간 꼬리(p99) → 구현·운영 복잡도. 지금 방식보다 분명히 나을 때만 바꾼다.
- 저장 순서(패스 먼저)는 지켜야 하는 규칙이다. 거꾸로 하면 3번처럼 데드락이 난다.

## 근거
- **정확성**: 3번만 무너졌다. 같은 패스에 경합이 있으면 기록을 먼저 넣는 순서에서 외래 키의 공유 잠금 때문에 데드락이 수백 번 났다. 중복 사용은 없었지만 500이다.
- **응답 시간**: 1·2·4번의 차이는 회차 사이의 흔들림보다 작고, 4번의 우위는 실행 순서의 영향과 구별되지 않는다. 기준의 "분명히 낫다"에 닿는 방식이 없다.
- **Redis 락(4번)**: 진 요청 대부분이 "이미 사용됨"이 아니라 "다시 시도"를 받아 데스크 안내가 부정확해지고(다시 누르면 그제야 이미 사용됨), 락을 잡은 요청이 링크 새로 만들기에 지면 나머지는 이미 걸러져 아무도 성공하지 못한다(섞임 71/300). 정확성은 여전히 DB가 지키므로 안전이 늘지도 않는다. 앞단에서 거르는 이득은 한 패스에 요청이 몰릴 때 나오는데, 패스마다 주인이 한 명이고 사용 처리는 하루 몇 건이라 그런 경합이 실제로 없다.
- **비관적 락(2번)**: 섞임에서 다시 시도가 없다는 장점이 있다. 대신 줄 서기가 길어질 때 꼬리가 크게 늘었고(첫 회차 경합 N8 1514ms, 섞임 1931ms), 링크 새로 만들기와 정확히 겹치는 일이 드물어 장점이 쓰일 일이 적다. 진 요청이 행 잠금을 기다리며 DB 연결을 쥐는 것은 1번도 같다(패스 UPDATE에서 기다린다).
- **1번**: 판정을 모두 통과했다. "다시 시도"는 링크 새로 만들기와 정확히 겹칠 때만 나오고, 같은 멱등 키로 다시 보내면 처리된다.
- 막는 장치가 서버 메모리가 아니라 DB의 제약이라 서버를 여러 대로 늘려도 그대로 안전하다.

## 포기한 것
- 링크 새로 만들기와 정확히 겹친 사용 처리는 "다시 시도"를 받는다(비관적 락이면 줄을 서서 처리된다).
- 측정은 한 PC에서 서버·DB·부하 도구를 함께 돌린 상대 비교이고, 방식의 실행 순서를 섞지 않았다. 운영 환경의 절대값이 아니며 수십 ms 차이는 가르지 못한다.

## 재검토 조건
- 같은 자원에 동시 요청이 실제로 몰리는 기능이 생길 때(선착순, 한정 수량) → 분산 락이나 대기열을 그 기능에서 다시 본다
- 서버를 여러 대로 늘리고 DB 경합이 지표에 드러날 때 → 방식의 실행 순서를 섞어 같은 방식으로 다시 잰다
- "다시 시도"가 데스크에서 자주 보일 때 → 비관적 락이나 서버 쪽 한 번 재시도를 본다
- 저장 순서(패스 먼저)를 바꾸는 변경이 있을 때 → 동시성 테스트와 이 부하 시험을 다시 돌린다
