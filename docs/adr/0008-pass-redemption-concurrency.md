# ADR-0008: 패스 중복 사용은 낙관적 락과 유니크 키로 막고, 분산 락은 쓰지 않는다

- 상태: 채택
- 날짜: 2026-10-18

## 배경
동탄고 패스는 한 번만 쓸 수 있다. 데스크 두 곳에서 같은 패스를 동시에 사용 처리하거나 버튼을 두 번 누르면 할인이 두 번 적용될 수 있다.

사용 처리는 한 트랜잭션에서 패스를 "사용됨"으로 바꾸고 사용 기록을 넣는다. 사용 기록에는 유니크 키가 둘 있다(패스 하나에 하나, 학생 한 명에 하나).
구현 중 동시성 테스트에서 같은 패스를 동시에 쓰면 데드락(500)이 나는 것을 발견했다. 사용 기록 INSERT의 외래 키 확인이 패스 행에 공유 잠금을 걸고,
ORM이 INSERT를 UPDATE보다 먼저 보내 두 요청이 서로의 공유 잠금을 기다렸다. 패스 UPDATE를 먼저 보내도록 고쳤다.

설계 때 중복 사용 방지 방식을 비교 실험으로 고르기로 했다. 같은 HTTP 부하를 걸어 정확성과 응답 시간을 쟀다.

## 선택지
모두 사용 기록의 두 유니크 키는 그대로 둔다.

1. **낙관적 락**: 패스를 잠그지 않고 읽고, 패스의 버전을 보며 먼저 고친 뒤 기록을 넣는다. 진 요청은 버전 충돌이나 유니크 키로 끝나고, 지금 상태를 다시 읽어 409로 답한다
2. **비관적 락**: 패스를 `SELECT … FOR UPDATE`로 읽어 같은 패스의 요청을 줄 세운다. 저장 순서는 1과 같다
3. **유니크 키만**: 잠그지 않고 읽고, 기록을 먼저 넣은 뒤 패스를 고친다(유니크 키가 먼저 막는다)
4. **Redis 분산 락 + 1**: 트랜잭션 밖에서 패스마다 Redis 락(SET NX + 토큰, 내 토큰일 때만 해제)을 잡는다. 못 잡으면 기다리지 않고 409(다시 시도)

## 측정

- 도구: k6. 실제 서버에 HTTP로(로그인, CSRF, 멱등 키, 보안 필터를 모두 거쳐) 부하를 건다. 사용 처리 요청의 응답 시간만 잰다
- 환경: 데스크톱 PC 한 대(14코어, 메모리 32GB)에서 서버, MySQL 8.4·Redis 7.4(컨테이너), k6를 함께 실행. DB 연결 풀 10, Tomcat 기본 설정. **숫자는 방식끼리의 상대 비교로만 뜻이 있다**
- 시나리오(각 300회 반복, 반복마다 새 패스·학생)
  - 경합 N8: 한 패스에 사용 처리 8개를 동시에(가상 사용자 10)
  - 경합 N32: 한 패스에 32개를 동시에(가상 사용자 4)
  - 분산: 서로 다른 패스에 1개씩(가상 사용자 32)
  - 섞임: 사용 처리 4개와 같은 패스의 링크 새로 만들기 4개를 동시에(가상 사용자 10)
- 정확성: 반복마다 사용 처리 성공이 정확히 1개(섞임은 많아야 1개), 서버 오류 0

| 방식 | 서버 오류(500) | 경합 N8 p99 | 경합 N32 p99 | 분산 p99 | 섞임 p99 | 섞임에서 사용 처리 성공 | 진 요청이 받는 답 |
|---|---|---|---|---|---|---|---|
| 1 낙관적 락 | 0 | 285ms | 383ms | 381ms | 381ms | 166/300 | 이미 사용됨(링크와 겹치면 다시 시도) |
| 2 비관적 락 | 0 | 384ms | 364ms | 346ms | 232ms | 300/300 | 이미 사용됨 |
| 3 유니크 키만 | 경합 N8 228건, N32 143건, 섞임 424건(모두 데드락) | 320ms | 420ms | 294ms | 352ms | 167/300 | 500 |
| 4 Redis 락 + 1 | 0 | 480ms | 280ms | 316ms | 243ms | 45/300 | 대부분 다시 시도(N32에서 9110/9300) |

- 네 방식 모두 중복 사용은 0건이었다(유니크 키가 막는다).
- 처음에 경합 N32를 가상 사용자 10(동시 연결 320)으로 돌렸더니 서버 수용량을 넘은 연결이 거절되어 방식과 무관한 실패가 섞였다. 연결 실패를 따로 세고 동시 연결을 128로 줄여 다시 쟀다. 그때 비관적 락만 거절 없이 모두 줄을 서서 p99가 1369ms까지 길어졌다.
- DB 연결 풀은 네 방식 모두 가득 찼다(활성 10/10, 대기 최대 117~120). 이 부하에서는 방식을 가르지 못했다.

## 결정
1번(낙관적 락 + 유니크 키, 패스를 먼저 고치고 기록을 나중에 넣는다)을 유지한다. 분산 락은 쓰지 않는다.

- 측정 전에 기준을 정했다: 정확성 → 응답 시간 꼬리(p99) → 구현·운영 복잡도. 지금 방식보다 분명히 나을 때만 바꾼다.
- 저장 순서(패스 먼저)는 지켜야 하는 규칙이다. 거꾸로 하면 3번처럼 데드락이 난다.

## 근거
- **정확성**: 3번만 무너졌다. 유니크 키는 중복을 막지만, 기록을 먼저 넣는 순서에서는 외래 키의 공유 잠금 때문에 부하 아래 데드락이 수백 번 났다. "중복은 없지만 500"이다.
- **응답 시간**: 1·2·4번의 차이는 수십~100ms 안이고 시나리오마다 순위가 바뀐다. 어느 하나가 늘 낫지 않다.
- **Redis 락(4번)**: 경합이 클 때 가장 빨랐다(앞단에서 걸러 DB까지 가는 요청이 준다). 그러나 진 요청 대부분이 "이미 사용됨"이 아니라 "다시 시도"를 받아 데스크 안내가 부정확해지고, 락을 잡은 요청이 링크 새로 만들기에 지면 나머지는 이미 걸러져 아무도 성공하지 못한다(섞임 45/300). 정확성은 여전히 DB가 지키므로 안전이 늘지도 않는다. 이득을 보는 상황(한 패스에 수십 개가 동시에)은 실제로 생기지 않는다. 사용 처리는 하루 몇 건이고 패스마다 주인이 한 명이다.
- **비관적 락(2번)**: 섞임에서 "다시 시도"가 없다는 장점이 있다. 대신 수용량을 넘는 부하에서 꼬리가 크게 길어졌고(1369ms), 기다리는 동안 DB 연결을 쥔다. 실제 경합이 드물어 장점이 쓰일 일이 적다.
- **1번**: 서버 오류 0, 응답 시간은 중간이다. "다시 시도"는 링크 새로 만들기와 정확히 겹칠 때만 나오고, 같은 멱등 키로 다시 보내면 처리된다.
- 막는 장치가 서버 메모리가 아니라 DB의 제약이라 서버를 여러 대로 늘려도 그대로 안전하다.

## 포기한 것
- 링크 새로 만들기와 정확히 겹친 사용 처리는 "다시 시도"를 받는다(비관적 락이면 줄을 서서 바로 처리된다).
- 같은 패스에 경합이 아주 클 때의 응답 시간은 Redis 락보다 길다.
- 측정은 한 PC에서 서버·DB·부하 도구를 함께 돌린 상대 비교다. 운영 환경의 절대값이 아니다.

## 재검토 조건
- 같은 자원에 동시 요청이 실제로 몰리는 기능이 생길 때(선착순, 한정 수량) → 분산 락이나 대기열을 그 기능에서 다시 본다
- 서버를 여러 대로 늘리고 DB 경합이 지표에 드러날 때 → 같은 방식으로 다시 잰다
- "다시 시도"가 데스크에서 자주 보일 때 → 비관적 락이나 서버 쪽 한 번 재시도를 본다
- 저장 순서(패스 먼저)를 바꾸는 변경이 있을 때 → 동시성 테스트와 이 부하 시험을 다시 돌린다
