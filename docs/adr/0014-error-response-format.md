# ADR-0014: 에러 응답 형식과 에러 코드 규칙

- 상태: 채택
- 날짜: 2026-10-10

## 배경
에러 응답은 RFC 9457 Problem Details를 쓴다(초기 설계에서 정한 원칙). 다만 `type`에 무엇을 넣을지, 클라이언트가 분기에 쓸 에러 코드의 이름 규칙과 위치는 정해지지 않았다. 모두 프론트와의 계약이라 한 번 쓰기 시작하면 바꾸기 어려워서, 첫 컨트롤러보다 먼저 정했다.
모듈 구조(ADR-0012)도 함께 고려해야 한다. `core`는 다른 모듈을 모르는 상태를 유지해야 하므로, 에러 코드를 `core` 한곳에 모으면 모듈의 업무 개념이 `core`로 들어온다.

## 선택지
**`type` 값**
1. 지정하지 않음(`about:blank`) + 확장 필드 `code` — 구현이 단순하고 죽은 링크가 없음 / `type`만 보는 범용 클라이언트는 에러 종류를 구분하지 못함
2. 코드별 URI(`https://…/errors/{code}`) — RFC가 권장하는 형태 / 그 주소에 설명 문서가 있어야 하는데 호스팅할 곳이 없음
3. URN(`urn:jey:error:{code}`) — 문서 없이도 고유함 / `code`와 정보가 중복되고 얻는 것이 없음

**에러 코드 이름**
1. `{모듈}_{사유}` 대문자 스네이크(`DONGTANPASS_PASS_EXPIRED`) — 읽기 쉽고 모듈끼리 겹치지 않음 / 이름이 길어짐
2. 숫자 코드(`4001`) — 짧음 / 뜻을 알려면 표를 봐야 하고, 번호대를 모듈별로 나눠 관리해야 함
3. 접두사 없는 이름(`PASS_EXPIRED`) — 짧음 / 모듈이 늘면 이름이 겹칠 수 있음

**에러 코드 위치**
1. 모듈별 enum — 코드를 추가할 때 `core`를 고치지 않음 / 전체 목록이 흩어짐
2. `core.shared`의 enum 하나 — 한 파일에서 전체 목록을 볼 수 있음 / 코드를 추가할 때마다 `core`를 고쳐야 하고, `core`가 다른 모듈의 업무 개념을 알게 됨

## 결정
`type`은 1번, 에러 코드 이름은 1번, 위치는 1번을 채택한다.

**응답 본문**

멤버는 `title`, `status`, `detail`, `instance`, `code`이고, 검증 실패일 때만 `errors`가 붙는다. Content-Type은 `application/problem+json`.

- `type`: 넣지 않는다. 지정하지 않으면 본문에 나오지 않고, RFC 9457은 `type`이 없으면 `about:blank`로 본다.
- `title`: HTTP 상태 문구(`Conflict` 등).
- `status`: HTTP 상태 코드.
- `detail`: 사용자에게 그대로 보여줄 안내 문구.
- `instance`: 요청 경로(쿼리스트링 제외).
- `code`: 클라이언트가 분기에 쓰는 에러 코드.
- `errors`: `[{ "field": "...", "message": "..." }]`
  - `field`는 오류가 난 본문 필드나 파라미터 이름이다. 특정 필드에 묶이지 않는 오류(객체 수준 제약 등)는 `null`이다.
  - `message`는 Bean Validation 문구다. 값의 형식이 맞지 않아 변환에 실패한 경우는 고정 문구("형식이 올바르지 않습니다.")를 쓴다.
- 문구는 요청의 `Accept-Language`와 무관하게 한국어다(로케일을 `ko_KR`로 고정).

아래는 예시다.

```json
{
  "title": "Bad Request",
  "status": 400,
  "detail": "입력값이 올바르지 않습니다.",
  "instance": "/api/v1/dongtanpass/passes",
  "code": "COMMON_VALIDATION_FAILED",
  "errors": [{ "field": "name", "message": "공백일 수 없습니다" }]
}
```

**에러 코드**

- `{모듈}_{사유}` 대문자 스네이크다. 한 번 내보낸 값은 바꾸지 않는다.
- 모듈과 무관한 공통 코드는 `COMMON_` 접두사를 쓴다.

| 코드 | 상태 | 쓰이는 경우 |
|---|---|---|
| `COMMON_VALIDATION_FAILED` | 400 | 입력값 검증 실패 (`errors` 포함) |
| `COMMON_BAD_REQUEST` | 400 | 그 밖의 요청 형식 오류 |
| `COMMON_UNAUTHENTICATED` | 401 | 인증 없음 |
| `COMMON_FORBIDDEN` | 403 | 권한 없음, CSRF 토큰 없음 |
| `COMMON_NOT_FOUND` | 404 | 대상 없음 |
| `COMMON_METHOD_NOT_ALLOWED` | 405 | 지원하지 않는 HTTP 메서드 |
| `COMMON_CONFLICT` | 409 | 현재 상태와 충돌 |
| `COMMON_INTERNAL_ERROR` | 500 | 서버 오류 |

**구조**

- `core.shared`에는 규약과 공통 코드만 둔다: `ErrorCode` 인터페이스, `CommonErrorCode`, 예외 `BusinessException`. 모듈별 코드는 각 모듈이 `ErrorCode`를 구현한 enum으로 가진다.
- 예외를 응답으로 바꾸는 변환기는 `core.web`에 둔다. 이 패키지의 타입은 다른 모듈에 공개하지 않지만, 변환은 모든 모듈의 컨트롤러에 적용된다. 변환기는 모듈별 예외·코드 타입을 모르고, 모듈 예외를 `BusinessException`과 `ErrorCode` 규약으로만 다룬다.
- 업무 예외는 `BusinessException`으로 던진다. `ResponseStatusException`처럼 코드가 없는 예외는 아래 표준 예외와 같이 처리돼 직접 넣은 사유 문구가 응답에 나가지 않는다.
- Spring MVC 표준 예외(404, 405, 본문 파싱 실패 등)는 HTTP 상태로 공통 코드를 붙이고, `detail`은 공통 코드의 문구로 바꾼다. 매핑이 없는 4xx는 `COMMON_BAD_REQUEST`, 5xx는 `COMMON_INTERNAL_ERROR`이며 HTTP 상태는 원래 값을 유지한다(예: 415 응답의 코드는 `COMMON_BAD_REQUEST`).
- 처리되지 않은 예외는 500과 `COMMON_INTERNAL_ERROR`, 일반 문구만 응답한다. 5xx로 응답하는 예외는 원인을 로그에 남긴다.
- 인증 실패(401)와 권한 없음(403)은 Security 필터에서 MVC의 `HandlerExceptionResolver`로 넘겨 같은 변환기가 응답을 쓴다. 변환에 실패하면 본문 없이 401·403 상태만 응답한다.
- CSRF 토큰이 없는 변경 요청은 인증 여부와 무관하게 403 `COMMON_FORBIDDEN`이다(CSRF 검사가 인증 검사보다 먼저 돈다).

## 근거
- 에러 설명 문서를 호스팅할 곳이 없다. 코드별 URI를 만들면 열리지 않는 주소가 계약에 들어간다.
- 프론트는 `code` 하나로 분기하고 `detail`을 그대로 보여주면 된다. `type`까지 해석할 이유가 없다.
- 접두사가 있으면 새 모듈이 추가돼도 코드 이름이 겹치지 않고, 코드만 봐도 어느 모듈에서 났는지 알 수 있다.
- 모듈이 자기 코드를 가지면 코드를 추가할 때 `core`를 고치지 않아도 된다. `core`가 다른 모듈의 업무 개념(패스 만료 등)을 알게 되지도 않는다. 감사 로그가 공통 봉투 타입만 구독하는 것(ADR-0012)과 같은 방식이다.
- 401·403의 본문을 Security 설정에서 직접 쓰면 변환기와 형식이 어긋날 수 있다. 한곳에서만 쓰게 한다.
- 표준 예외의 Spring 기본 문구는 영어이고 사용자에게 보여줄 문구가 아니다. 프론트가 `detail`을 그대로 보여줄 수 있도록 공통 코드의 문구로 통일한다.
- 값 변환 실패 문구에는 내부 타입 이름과 사용자가 입력한 값이 들어 있다. 잘못된 칸에 넣은 개인정보가 응답으로 되돌아가지 않게 고정 문구로 바꾼다.

## 포기한 것
- `type`만 보는 RFC 9457 범용 클라이언트는 에러 종류를 구분하지 못한다. `code` 확장 필드를 알아야 한다.
- 표준 예외에서 Spring이 주는 구체적인 원인 문구("필수 파라미터 `size` 누락" 같은 것)는 응답에 나가지 않는다.
- 안내 문구가 한국어로 고정된다. 다국어를 지원하려면 구조를 바꿔야 한다.
- 에러 코드가 모듈마다 흩어져 있어 전체 목록을 한 파일에서 볼 수 없다.
- 매핑이 없는 4xx(413, 415, 429 등)는 문구가 "요청 형식이 올바르지 않습니다."로 뭉뚱그려진다.

## 재검토 조건
- API 문서 사이트가 생겨 코드별 설명 주소를 줄 수 있을 때
- API를 외부(연계 학원 시스템 등)에 공개할 때
- 다국어 안내 문구가 필요해질 때
- 파일 업로드나 요청 제한이 생겨 413·429 전용 코드가 필요해질 때
