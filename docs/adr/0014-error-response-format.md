# ADR-0014: 에러 응답 형식과 에러 코드 규칙

- 상태: 채택
- 날짜: 2026-10-10

## 배경
에러 응답은 RFC 9457 Problem Details로 하기로 정해져 있었지만, `type`에 무엇을 넣을지와 클라이언트가 분기에 쓸 에러 코드의 이름 규칙은 정해지지 않았다. 둘 다 프론트와의 계약이라 한 번 쓰기 시작하면 바꾸기 어렵다. 첫 컨트롤러를 만들기 전에 고정한다.
모듈 구조(ADR-0012)도 함께 고려해야 한다. `core`는 다른 모듈을 모르는 상태를 유지해야 하므로, 에러 코드를 한곳에 모으는 방식은 쓸 수 없다.

## 선택지
**`type` 값**
1. `about:blank` + 확장 필드 `code` — 구현이 단순하고 죽은 링크가 없음 / `type`만 보는 범용 클라이언트는 에러 종류를 구분하지 못함
2. 코드별 URI(`https://…/errors/{code}`) — RFC가 권장하는 형태 / 그 주소에 설명 문서가 있어야 하는데 호스팅할 곳이 없음
3. URN(`urn:jey:error:{code}`) — 문서 없이도 고유함 / `code`와 정보가 중복되고 얻는 것이 없음

**에러 코드 이름**
1. `{모듈}_{사유}` 대문자 스네이크(`GOPASS_PASS_EXPIRED`) — 읽기 쉽고 모듈끼리 겹치지 않음 / 이름이 길어짐
2. 숫자 코드(`4001`) — 짧음 / 뜻을 알려면 표를 봐야 하고, 번호대를 모듈별로 나눠 관리해야 함
3. 접두사 없는 이름(`PASS_EXPIRED`) — 짧음 / 모듈이 늘면 이름이 겹칠 수 있음

## 결정
- 응답 본문은 `title`, `status`, `detail`, `instance`, `code`로 구성한다. Content-Type은 `application/problem+json`.
  - `type`: `about:blank`. 이 값일 때 Spring은 본문에서 `type`을 생략하고, RFC 9457은 생략된 `type`을 `about:blank`로 본다.
  - `title`: HTTP 상태 문구(`Conflict` 등).
  - `detail`: 사용자에게 보여줄 한국어 안내 문구.
  - `code`: 클라이언트가 분기에 쓰는 에러 코드.
  - `errors`: 검증 실패일 때만 넣는다. `[{ "field": "...", "message": "..." }]`
- 에러 코드는 `{모듈}_{사유}` 대문자 스네이크다. 모듈과 무관한 공통 코드는 `COMMON_` 접두사를 쓴다(`COMMON_VALIDATION_FAILED`, `COMMON_UNAUTHENTICATED`, `COMMON_NOT_FOUND` 등).
- `core.shared`에는 규약만 둔다: `ErrorCode` 인터페이스, 공통 코드 `CommonErrorCode`, 예외 기반 클래스 `BusinessException`. 모듈별 코드는 각 모듈이 `ErrorCode`를 구현한 enum으로 가진다.
- 예외를 응답으로 바꾸는 변환기는 `core.web`에 둔다. 이 패키지는 다른 모듈에 공개하지 않으며, 변환기는 `BusinessException` 기반 타입만 안다.
- Spring MVC 표준 예외(404, 405, 본문 파싱 실패 등)는 HTTP 상태로 공통 코드를 붙이고, `detail`은 Spring 기본 문구 대신 공통 코드의 문구를 쓴다.
- 처리되지 않은 예외는 500과 `COMMON_INTERNAL_ERROR`, 일반 문구만 응답한다. 원인은 로그에만 남긴다.
- 인증 실패(401)와 권한 없음(403)은 Security 필터에서 MVC의 `HandlerExceptionResolver`로 넘겨 같은 변환기가 응답을 쓴다.

```json
{
  "title": "Bad Request",
  "status": 400,
  "detail": "입력값이 올바르지 않습니다.",
  "instance": "/api/v1/gopass/passes",
  "code": "COMMON_VALIDATION_FAILED",
  "errors": [{ "field": "name", "message": "공백일 수 없습니다" }]
}
```

## 근거
- 에러 설명 문서를 호스팅할 곳이 없다. 코드별 URI를 만들면 열리지 않는 주소가 계약에 들어간다.
- 프론트는 `code` 하나로 분기하고 `detail`을 그대로 보여주면 된다. `type`까지 해석할 이유가 없다.
- 접두사가 있으면 새 모듈이 추가돼도 코드 이름이 겹치지 않고, 코드만 봐도 어느 모듈에서 났는지 알 수 있다.
- 모듈이 자기 코드를 가지면 코드를 추가할 때 `core`를 고치지 않아도 된다. `core`가 다른 모듈의 업무 개념(패스 만료 등)을 알게 되지도 않는다. 감사 로그가 공통 봉투 타입만 구독하는 것(ADR-0012)과 같은 방식이다.
- 401·403의 본문을 Security 설정에서 직접 쓰면 변환기와 형식이 어긋날 수 있다. 한곳에서만 쓰게 한다.
- 표준 예외의 Spring 기본 문구는 영어이고 내부 정보(파서 메시지, 리소스 경로)가 섞일 수 있다.

## 포기한 것
- `type`만 보는 RFC 9457 범용 클라이언트는 에러 종류를 구분하지 못한다. `code` 확장 필드를 알아야 한다.
- 표준 예외에서 Spring이 주는 구체적인 원인 문구("필수 파라미터 `size` 누락" 같은 것)는 응답에 나가지 않는다.
- 안내 문구가 코드에 한국어로 고정된다. 다국어를 지원하려면 구조를 바꿔야 한다.
- 에러 코드가 모듈마다 흩어져 있어 전체 목록을 한 파일에서 볼 수 없다.

## 재검토 조건
- API 문서 사이트가 생겨 코드별 설명 주소를 줄 수 있을 때
- API를 외부(연계 학원 시스템 등)에 공개할 때
- 다국어 안내 문구가 필요해질 때
