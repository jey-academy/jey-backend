# ADR-0015: 금액 표현과 반올림 규칙

- 상태: 채택
- 날짜: 2026-10-10

## 배경
수강료 계산, 청구, 결제가 모두 금액을 다룬다. 금액을 기본 타입으로 들고 다니면 오차가 생기거나, 어디서 반올림했는지 추적할 수 없게 된다.
수강료 공식은 `기준수강료(8회분) × (1 − 할인율) ÷ 8 × 수업횟수`이고, 결과가 원 단위로 떨어지지 않을 때 어떻게 끊을지 정해야 했다. 기존 납부 일지의 금액과 계산 결과가 같아야 한다(280,000원, 5%, 9회 → 299,250원).
학원에서 확인한 규칙은 "8로 나누고 횟수를 곱한 뒤, 최종 금액에서 소수점만 버린다"이다.

## 선택지
**금액 타입**
1. `long`(원 단위 정수) — 단순하고 빠름 / 계산 중간의 소수(304,593.75)를 담을 수 없어 중간에 끊게 됨. 금액 자리에 다른 숫자를 넣어도 컴파일됨
2. `BigDecimal` 기반 값 객체 `Money` — 중간 계산의 정밀도 유지, 타입으로 구분됨 / 객체 생성 비용, 매핑 코드 필요

**끊는 시점**
1. 회당 단가 단계 — 단가가 깔끔한 숫자가 됨 / 횟수를 곱하면서 버린 금액이 배로 불어남
2. 최종 금액 단계 — 오차가 한 번만 생김 / 중간 값이 소수일 수 있음

**단위와 방향**
1. 소수점 이하(1원 미만) 버림 — 304,593.75 → 304,593원
2. 10원 미만 버림 — 304,593.75 → 304,590원
3. 반올림 — 304,593.75 → 304,594원

**나누기 구현**
1. 나눈 값을 정해진 자릿수에서 자동으로 자름 — 항상 계산됨 / 자른 값에 다시 곱하면 오차가 커짐. `100 ÷ 3 × 3`이 99.99…가 되고 소수점을 버리면 99원이 됨
2. 나누어떨어지지 않으면 예외 — 오차가 없음 / 입력에 따라 청구 등록 자체가 막힘
3. 나누기를 항상 마지막에 두고 끊는 규칙과 한 번에 처리 — 오차도 예외도 없음 / 나눈 뒤에 다른 연산을 이어 쓸 수 없음

## 결정
금액 타입은 2번, 끊는 시점은 2번, 단위와 방향은 1번, 나누기 구현은 3번을 채택한다.

- 금액은 `core.shared`의 `Money`로 다룬다. `double`은 쓰지 않는다.
- `Money`는 0 이상만 허용한다. 음수로 만들거나 빼서 음수가 되면 예외다.
- **반올림 규칙: 최종 금액에서 소수점 이하(1원 미만)를 버린다.** 중간 계산에서는 끊지 않는다.
  - 280,000원, 5%, 9회 → 299,250원 (그대로)
  - 285,000원, 5%, 9회 → 304,593.75 → 304,593원
- 끊는 규칙은 `RoundingPolicy`(단위, 방향) 값으로 넘긴다. 확정된 규칙은 `RoundingPolicy.ONE_WON_DOWN`이다.
- `Money`는 스스로 끊지 않는다. 금액이 끊기는 곳은 `dividedBy(나누는 수, 정책)`과 `round(정책)` 두 군데뿐이다.
- 코드에서는 곱셈을 모두 끝낸 뒤 마지막에 나눈다: `기준수강료 × (1 − 할인율) × 수업횟수 ÷ 8`. 학원의 계산 순서(나누고 곱함)와 적는 순서는 다르지만, 중간에 끊지 않으면 곱셈과 나눗셈은 순서를 바꿔도 값이 같다. 두 순서의 결과가 같다는 것은 테스트로 확인한다(기준수강료 15만~45만 원, 할인율 5종, 1~12회).
- 금액이 같으면 같은 `Money`다(`1000.0` = `1000`).
- JSON에서는 숫자 하나(`299250`)로 주고받는다.

## 근거
- 최종 단계에서 한 번만 끊으면 오차가 1원 미만으로 한 번만 생긴다. 단가에서 끊으면 횟수만큼 불어난다.
- 나누기를 마지막에 두면 나누어떨어지지 않는 경우에도 수학적으로 정확한 몫에서 끊은 값이 나온다. 중간에 자르지 않으므로 순서에 따른 오차가 없고, 입력 때문에 계산이 실패하는 일도 없다. 청구 등록은 데스크 업무라 계산 예외로 막히면 안 된다.
- 8로 나누는 지금의 공식은 어느 순서로 해도 정확하다. 나누기와 끊기를 한 메서드로 묶은 것은 나누는 수가 달라지는 계산(일할 계산 등)이 생겼을 때 "잘린 금액에 다시 곱하는" 실수를 코드로 쓸 수 없게 하기 위해서다.
- 음수 금액은 정상 입력으로는 나오지 않는다. 나왔다면 잘못된 청구가 만들어지기 전에 멈추는 편이 낫다.
- `BigDecimal`은 `1000.0`과 `1000`을 다르게 본다. 생성할 때 표현을 하나로 맞춰야 비교와 Map 키가 기대대로 동작한다.
- 금액은 원 단위 정수라 JSON 숫자로 내보내도 JavaScript 정수 범위 안이다. 프론트가 문자열을 숫자로 바꿀 필요가 없다.

## 포기한 것
- 환불·차액 같은 음수 금액을 `Money`로 표현할 수 없다. 필요해지면 별도 타입이나 허용 범위를 다시 정해야 한다.
- 나눈 결과를 끊지 않은 채로 다음 계산에 넘길 수 없다. 코드의 계산 순서가 학원에서 말하는 순서(나누고 곱함)와 글자 그대로 같지는 않다.
- 1원 미만은 항상 학원이 덜 받는 쪽으로 끊긴다.
- 확정된 규칙이 지금은 코드의 상수다. 설정 파일로 바꾸는 일은 수강료 계산기를 만들 때 한다.

## 재검토 조건
- 환불이나 차액 처리를 구현할 때 (음수 금액)
- 반 나눔으로 청구 라인이 여러 개일 때 라인마다 끊을지 합산 후 끊을지 정해야 할 때
- 기존 납부 일지의 금액과 계산 결과가 1원이라도 다른 사례가 나올 때 (스프레드시트의 부동소수점 계산과 차이가 날 수 있음)
- 끊는 규칙이 지점이나 반마다 달라져야 할 때
