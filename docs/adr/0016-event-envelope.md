# ADR-0016: 이벤트 봉투

- 상태: 채택
- 날짜: 2026-10-10

## 배경
모듈끼리는 도메인 이벤트로 연결한다(ADR-0012). 이벤트마다 형식이 다르면 두 가지가 안 된다.
- 같은 이벤트가 두 번 도착했을 때 걸러낼 기준이 없다. 리스너는 실패하면 다시 실행되므로 항상 멱등이어야 한다.
- 감사 로그가 모든 이벤트를 기록하려면 개별 이벤트 타입을 알아야 한다. 감사 로그는 `core`에 있고 `core`는 다른 모듈에 의존하면 안 된다.

그래서 모든 이벤트가 공통으로 갖는 정보(봉투)를 정한다: 이벤트 ID, 이름, 버전, 발생 시각, 지점.

## 선택지
**봉투의 형태**
1. 인터페이스 + 봉투 정보 값 — 이벤트 record가 인터페이스를 구현하고 봉투 정보를 필드로 가짐. 구체 타입이 그대로 남아 리스너 매칭과 발행 기록 저장·복원이 자연스러움 / 이벤트마다 봉투 정보 필드를 선언해야 함
2. 제네릭 래퍼 `Envelope<T>` — 내용물과 봉투가 분리돼 구조가 깔끔함 / 실행 중에는 `T`가 지워져서 리스너가 내용물 타입으로 골라 받기 어렵고, 발행 기록에서 복원할 때 내용물 타입을 알 수 없음
3. 공통 부모 클래스 — 필드를 물려받음 / record를 쓸 수 없고 상속에 묶임

**이벤트 ID**
1. UUID v4(무작위) — JDK 기본 제공 / 순서가 없어 DB 인덱스 곳곳에 흩어져 들어감
2. UUID v7(시간순) — ID 순서가 발생 순서, 인덱스 뒤쪽에만 쌓임 / Java 21에 생성기가 없음
3. DB 자동 증가 번호 — 짧고 순서가 있음 / 저장하기 전에는 ID를 알 수 없고, 나중에 다른 시스템으로 내보낼 때 겹칠 수 있음

**UUID v7 생성**
1. 라이브러리 추가 — 검증된 구현, 같은 밀리초 안의 순서까지 보장 가능 / 의존성이 하나 늘어남
2. 직접 구현 — 의존성 없음, 15줄 / 같은 밀리초 안의 순서는 보장하지 않음

## 결정
봉투의 형태는 1번, 이벤트 ID는 2번, 생성은 2번을 채택한다.

- 모든 도메인 이벤트는 `core.shared`의 `DomainEvent`를 구현하는 record로 만들고, 봉투 정보 `EventMetadata`와 자기 내용을 필드로 가진다.
  ```java
  record PaymentCompleted(EventMetadata metadata, long paymentId, Money amount) implements DomainEvent { }
  ```
- `EventMetadata`의 필드
  - `eventId`: UUID v7. 같은 이벤트인지 가리는 기준이다.
  - `eventType`: `{모듈}.{사건}` 소문자 kebab-case(예: `billing.payment-completed`). 형식이 틀리면 만들 수 없다. 한 번 내보낸 이름은 바꾸지 않는다.
  - `version`: 1부터. 필드 추가는 같은 버전에서 하고, 의미를 바꾸거나 필드를 없애야 하면 버전을 올린다.
  - `occurredAt`: 사건이 일어난 시각(ADR-0017의 시점 규칙).
  - `campusId`: 사건이 속한 지점. 지점과 무관한 사건은 `null`.
- 봉투 정보는 `EventMetadata.create(eventType, version, campusId, clock)`으로 만든다. ID와 발생 시각은 주입받은 시계에서 얻는다.
- 모든 이벤트를 받아야 하는 쪽(감사 로그)은 `DomainEvent` 타입을 구독한다.
- 이벤트에는 개인정보를 넣지 않는다. ID만 넣고 필요한 쪽이 조회한다.
- 이벤트는 Spring Modulith의 이벤트 발행 기록(Event Publication Registry)에 JSON으로 저장된다. 리스너가 실패하면 기록에 남고, 다시 보내면 같은 내용(같은 `eventId`)으로 도착한다.
- 바깥 시스템으로 내보낼 때의 모양(`{ eventId, eventType, version, occurredAt, campusId, payload }`처럼 내용을 `payload`로 감싼 형태)은 실제로 내보내게 될 때 변환해서 만든다. 프로세스 안에서는 위 record 그대로 다룬다.

## 근거
- 인터페이스 방식은 이벤트의 구체 타입이 그대로 남는다. 리스너는 받고 싶은 타입을 그대로 적으면 되고, 발행 기록도 타입 이름과 JSON만으로 원래 객체를 복원한다. 실패 후 재전송에서 같은 내용으로 복원되는 것을 통합 테스트로 확인했다.
- 제네릭 래퍼는 실행 중에 내용물 타입이 지워진다. 리스너 매칭과 복원을 맞추려면 별도 장치가 필요한데, 얻는 것은 구조의 깔끔함뿐이다.
- `eventId`가 발행 시점에 정해지고 재전송에서도 유지돼야 리스너가 "이미 처리한 이벤트"를 가릴 수 있다.
- 시간순 ID는 발행 기록이나 로그를 ID로 정렬하면 발생 순서가 된다. 무작위 ID보다 인덱스에 덜 흩어져 들어간다.
- 직접 구현은 짧고 단순하다. 같은 밀리초 안의 순서까지는 필요하지 않다. 정확한 순서가 필요하면 `occurredAt`을 본다.
- 이벤트 이름 형식을 생성 시점에 검사하면 틀린 이름이 발행 기록에 남기 전에 막을 수 있다.

## 포기한 것
- 이벤트 record마다 `EventMetadata metadata` 필드와 생성 코드를 적어야 한다.
- 프로세스 안의 JSON 모양(`metadata`가 안쪽에 있음)과 바깥으로 내보낼 모양(`payload`가 안쪽에 있음)이 다르다. 내보낼 때 변환 코드가 필요하다.
- 같은 밀리초에 만든 ID끼리는 순서가 섞일 수 있다.
- `eventType`의 모듈 접두사가 실제 모듈과 맞는지는 검사하지 않는다(형식만 본다).
- 발행 기록의 `serialized_event` 컬럼은 4,000자다. 그보다 큰 이벤트는 저장되지 않으므로 이벤트에는 ID 위주의 작은 내용만 넣는다.

## 재검토 조건
- 이벤트를 바깥 시스템(메시지 브로커 등)으로 내보내게 될 때 (바깥 모양으로의 변환, 스키마 호환 규칙)
- 같은 밀리초 안의 순서가 중요한 처리가 생길 때 (라이브러리 도입 또는 순번 추가)
- 이벤트 이름과 모듈이 어긋나는 사례가 생길 때 (모든 `DomainEvent` 구현체를 검사하는 테스트 추가)
