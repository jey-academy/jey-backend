# ADR-0017: 날짜·시간 규칙

- 상태: 채택
- 날짜: 2026-10-10

## 배경
날짜와 시간은 세 군데에서 어긋나기 쉽다.
- **현재 시각을 구하는 방법**: 코드가 `LocalDate.now()`를 직접 부르면 테스트가 실행하는 날짜에 따라 결과가 달라진다. 패스 유효기간(발급일 + 1개월) 같은 규칙을 검증하려면 시각을 고정할 수 있어야 한다. 또 서버의 기본 시간대가 UTC면 한국 시간 0시~9시 사이에 "오늘"이 하루 전 날짜로 나온다.
- **타입**: "언제 일어났나"와 "며칠인가"는 다른 개념인데 한 타입으로 섞어 쓰면 시간대 변환에서 날짜가 하루 밀린다.
- **JSON 표현**: 프론트와의 계약이라 API마다 다르면 안 된다.

학원은 한국에만 있고 사용자도 모두 한국 시간대에 있다.

## 선택지
**"언제 일어났나"(시점)의 타입**
1. `Instant` — 시간대와 무관한 절대 시각. 코드와 API에서 변환할 것이 없음 / JSON이 UTC(`…Z`)라 사람이 읽을 때 9시간을 더해야 함
2. `OffsetDateTime`(+09:00) — JSON에 한국 시각이 그대로 보임 / 값마다 시간대가 붙어 있어 같은 시점인데 표현이 다른 값이 생김
3. `LocalDateTime` — 단순함 / 시간대 정보가 없어 서버 설정이 바뀌면 다른 시점이 됨

**현재 시각을 구하는 방법**
1. `now()` 직접 호출 — 가장 짧음 / 테스트에서 고정할 수 없고 서버 시간대에 의존
2. `Clock` 빈 주입 — 테스트에서 바꿔 끼울 수 있고 시간대를 한곳에서 정함 / 시각이 필요한 곳마다 `Clock`을 받아야 함

## 결정
시점의 타입은 1번, 현재 시각은 2번을 채택한다.

**타입**

| 개념 | 예 | 타입 | JSON |
|---|---|---|---|
| 시점 (언제 일어났나) | 결제 시각, 이벤트 발생 시각 | `Instant` | `"2026-11-03T01:21:05.123Z"` (UTC) |
| 날짜 (며칠인가) | 발급일, 만료일, 납부일 | `LocalDate` | `"2026-11-03"` |
| 월 | 수강료 대상월 | `YearMonth` | `"2026-11"` |

- `LocalDateTime`, `java.util.Date`는 쓰지 않는다.
- 시점을 JSON으로 읽을 때는 시간대가 붙은 표현(`2026-11-03T10:21:05.123+09:00`)도 같은 시점으로 읽는다.
- 화면에 보일 때 한국 시각으로 바꾸는 것은 프론트가 한다.
- DB의 시점 컬럼(`DATETIME(6)`)에는 한국 시각으로 저장한다. DB를 직접 열어 봤을 때 변환 없이 읽히게 하기 위해서다. 코드에서 다루는 타입(`Instant`)과 JSON 표현(UTC)은 그대로다.
  - 저장하고 읽을 때 JPA 설정이 `Asia/Seoul`로 바꾼다(`hibernate.jdbc.time_zone`, `preferred_instant_jdbc_type=TIMESTAMP`). 모든 `Instant` 컬럼에 적용되며, 이벤트 발행 기록 테이블의 시각 컬럼도 포함된다.
  - 한국에는 서머타임이 없어서 시간대 없는 값도 한 시점으로 정해진다.
  - SQL에서 `NOW()` 같은 DB의 시계는 쓰지 않는다. DB 접속의 시간대에 따라 값이 달라진다.

**현재 시각**

- 현재 시각은 주입받은 `Clock`에서만 얻는다: `clock.instant()`, `LocalDate.now(clock)`, `YearMonth.now(clock)`.
- `Clock` 빈의 시간대는 `Asia/Seoul`이다. "오늘"은 서버의 기본 시간대와 무관하게 한국 날짜다.
- `Instant.now()`, `LocalDate.now()` 같은 인자 없는 `now()`, `System.currentTimeMillis()`, `new Date()`, `Clock.systemDefaultZone()`, `Clock.systemUTC()`는 운영 코드에서 쓸 수 없다. 테스트(ArchUnit)가 검사하며, 쓰면 빌드가 실패한다.
- 테스트에서 시각을 고정하는 방법
  - 도메인 로직은 `Clock`을 인자나 생성자로 받게 만들고, 단위 테스트에서 `Clock.fixed(…)`를 넘긴다.
  - 스프링 컨텍스트를 띄우는 테스트에서 시각을 고정해야 하면 테스트용 설정으로 `Clock` 빈을 바꿔 끼운다.

## 근거
- 시점을 `Instant`로 두면 코드와 API에서는 비교, 전달 어디에서도 시간대를 해석할 일이 없다. 시점(`Instant`)에 시간대가 개입하는 곳은 화면 표시와 DB 저장 두 곳뿐이고, DB 변환은 JPA 설정 한곳에서 한다.
- 발급일이나 대상월은 시각이 아니라 달력상의 날짜다. 시점 타입에 담으면 시간대 변환 때 날짜가 하루 밀릴 수 있다.
- 규칙을 문서에만 적으면 지켜지지 않는다. `now()` 직접 호출은 눈에 잘 띄지 않고 대부분의 테스트를 통과하므로 빌드에서 막는다.
- "오늘"을 정하는 시간대는 `Clock` 빈에서, DB 저장 시간대는 JPA 설정에서 정한다. 둘 다 `Asia/Seoul`이며 서버나 컨테이너의 시간대 설정에 기대지 않는다. 테스트는 JVM 시간대를 한국도 UTC도 아닌 곳으로 고정하고 돌려서 이 점을 확인한다.

## 포기한 것
- API 응답의 시각이 UTC라 사람이 그대로 읽으면 9시간 차이가 난다.
- DB의 시각은 한국 시각이고 컬럼에 시간대 정보가 없다. DB 값만 보고는 시간대를 알 수 없으므로, 이 규칙을 모르는 도구로 읽으면 9시간 어긋난다.
- 시각이 필요한 클래스마다 `Clock`을 받아야 한다.
- 여러 시간대의 사용자는 고려하지 않는다.

## 재검토 조건
- 해외 지점이나 다른 시간대의 사용자가 생길 때 ("오늘"의 기준을 지점별로 정해야 하고, DB 저장도 UTC로 바꿔야 함)
- 영업 시간처럼 날짜 없이 시각만 다루는 값이 필요해질 때 (`LocalTime` 규칙 추가)
- 달력상의 날짜와 시각을 함께 다뤄야 하는 값(예약 시각 등)이 생길 때
