# ADR-0019: 인증은 서버 세션으로

- 상태: 채택
- 날짜: 2026-10-10

## 배경
직원, 관리자, 연계 학원이 아이디와 비밀번호로 로그인해야 한다. 초기 설계는 JWT를 httpOnly 쿠키에 담는 방식이었는데, 구현에 앞서 다시 검토했다.

이 서비스의 조건은 이렇다.
- 서버는 한 대짜리 모놀리스이고 Redis를 이미 쓴다.
- 퇴사한 직원이나 계약이 끝난 연계 학원의 계정은 로그인돼 있더라도 바로 막을 수 있어야 한다.
- 데스크 직원은 지점마다 한 명이고, 화면을 하루 종일 켜 두고 쓴다.
- 프론트는 브라우저에서 도는 웹앱 하나이고, 인증 정보를 직접 다루지 않는다(httpOnly 쿠키).

## 선택지
1. **JWT(액세스 + 리프레시)를 쿠키로** — 서버가 상태를 들지 않아도 토큰만으로 인증. 서버 종류가 여럿일 때 유리 / 발급한 토큰은 만료 전까지 유효해서 즉시 차단하려면 리프레시 토큰 저장, 교체, 차단 목록을 직접 만들어야 함. 프론트에도 재발급 처리가 필요
2. **서버 세션(Redis 저장)** — 세션을 지우면 그 자리에서 로그아웃. 쓰는 동안 자동 연장. Spring Security와 Spring Session의 기능으로 구현 / 요청마다 Redis 조회. 다른 서비스가 사용자를 직접 검증하기 어려움. 즉시 차단을 하려면 계정별로 세션을 찾는 색인이 필요

## 결정
2번을 채택한다.

**방식**

- 인증 상태는 서버 세션에 두고 Redis에 저장한다(Spring Session). 브라우저에는 세션 쿠키만 준다.
- 새 의존성: `spring-boot-starter-session-data-redis` (Spring Boot가 버전을 관리).
- 세션 쿠키 `SESSION`: `HttpOnly`, `SameSite=Lax`, `Secure`(HTTPS가 없는 로컬에서만 끔). 속성은 코드에서 직접 정한다. Spring Boot의 기본 구성은 실행 환경에 따라 다른 곳에서 값을 읽어 오기 때문이다.
- 로그인하면 세션 ID를 바꾼다(세션 고정 공격 방지).
- 인증 없는 요청은 세션을 만들지 않는다.
- 세션에서 "누구인가"를 가리키는 이름(`Authentication#getName`)은 아이디가 아니라 계정 ID다. 세션 색인과 로그가 이 값을 쓴다.
- Redis 명령과 연결의 제한 시간은 2초다. Redis가 응답하지 않으면 요청은 2초 안에 실패한다.

**세션의 수명**

| | 마지막 요청 후 만료 | 로그인 후 최대 유지 |
|---|---|---|
| `STAFF` | 12시간 | 16시간 |
| `ADMIN`, `PARTNER` | 2시간 | 12시간 |

- 만료 시간은 마지막 요청 기준이라 쓰는 동안 계속 연장된다. 데스크 화면은 하루 종일 켜 두므로 직원은 길게, 권한이 큰 관리자와 학원 밖에서 접속하는 연계 학원은 짧게 둔다.
- 화면이 주기적으로 요청을 보내면 만료 시간만으로는 세션이 끝나지 않는다. 그래서 로그인 시점부터의 최대 유지 시간을 따로 둔다. 이 시간이 지나면 쓰는 중이어도 다시 로그인해야 한다.
- 두 값 모두 설정값이다(`jey.auth.session-timeout`, `jey.auth.session-max-lifetime`). 설정에 없는 역할은 만료 2시간, 최대 유지 12시간이 적용된다.
- 최대 유지 시간은 로그인할 때 세션에 끝나는 시각을 적어 두고, 요청마다 필터가 확인한다. 로그인 정보나 그 시각이 없거나 읽을 수 없는 세션은 끊는다.

**즉시 차단**

- 세션은 계정 ID로 색인한다. 계정을 차단하면(`AccountService#disable`) 그 계정의 세션을 모두 지운다. 끊긴 세션의 다음 요청은 401을 받는다.
- 이미 처리 중이던 요청은 끝까지 처리된다.
- 차단과 거의 동시에 진행 중이던 로그인은 드물게 살아남을 수 있다. 로그인은 비밀번호를 검증한 뒤 세션을 만들기 직전에 계정 상태를 DB에서 다시 읽어 이 틈을 수 밀리초로 줄이지만, 완전히 닫지는 않는다. 살아남은 세션도 최대 유지 시간이 지나면 끊긴다.
- 세션에는 로그인 시점의 이름·역할·지점이 들어 있다. 계정의 역할이나 지점을 바꿀 때도 세션을 끊어(`UserSessions#terminateAll`) 다시 로그인하게 해야 반영된다.
- 2026-10 기준으로 계정을 차단하거나 역할·지점을 바꾸는 API는 아직 없다. 계정 관리 기능을 만들 때 위 서비스를 호출한다.

**계정과 로그인**

- 1차 로그인 대상은 직원(`STAFF`), 관리자(`ADMIN`), 연계 학원(`PARTNER`)이다. 학부모는 로그인 없이 링크로 패스를 연다.
- 직원은 소속 지점이 있어야 하고, 관리자와 연계 학원은 지점이 없다. 이 조합이 아니면 계정을 만들 수 없다.
- 아이디는 영문 소문자, 숫자, `.`, `_`, `-`만 쓸 수 있고 3~50자다. 앞뒤 공백을 떼고 소문자로 맞춰 저장하며, 로그인할 때도 같은 규칙으로 찾는다. 허용하지 않는 문자가 섞인 입력은 DB에 묻지 않고 실패시킨다.
- 비밀번호는 BCrypt로 해시하고, 해시 앞에 알고리즘 이름을 붙여 저장한다(`{bcrypt}…`).
- 로그인 실패는 이유를 구분하지 않는다. 아이디가 없든, 비밀번호가 틀렸든, 비활성 계정이든 401 `AUTH_INVALID_CREDENTIALS`와 같은 문구다.
- 비활성 계정만 해시 계산 없이 빨리 실패하는 일이 없도록, 비활성 여부는 비밀번호가 맞은 뒤에 확인한다. 없는 아이디도 Spring Security가 가짜 해시를 한 번 계산한다. 어느 경우든 해시 계산은 한 번이다(응답 시간 자체를 측정해 검증한 것은 아니다).
- 로그에는 실패한 예외의 종류만 남긴다. 다만 비밀번호는 맞았는데 비활성인 경우에는 계정 ID를 함께 남긴다. 없는 아이디와 틀린 비밀번호는 로그에서도 구분되지 않는다. 입력한 아이디는 어떤 경우에도 남기지 않는다(아이디 칸에 비밀번호를 잘못 넣는 일이 흔하다).
- 계정 조회 중 DB 오류 같은 내부 문제는 로그인 실패로 응답하지 않고 500으로 응답하며 원인을 로그에 남긴다.
- 에러 코드 접두사는 `AUTH_`다. `core`는 API 경로(ADR-0013)와 마찬가지로 모듈 이름 대신 하위 영역 이름을 쓴다.
- 계정이 하나도 없을 때는 실행 환경의 설정값(`jey.auth.initial-admin`)으로 관리자 한 명을 만든다. 계정이 이미 있으면 아무것도 하지 않는다. 운영에서는 계정도 설정값도 없으면 서버가 뜨지 않는다.

**API**

| 주소 | 응답 | 동작 |
|---|---|---|
| `GET /api/v1/auth/csrf` | 204 | CSRF 토큰 쿠키 발급 (공개) |
| `POST /api/v1/auth/login` | 200 | `{ loginId, password }`로 로그인. 사용자 정보와 세션 쿠키 |
| `GET /api/v1/auth/me` | 200 | 로그인한 사용자: `{ id, loginId, name, role, campusId }` |
| `POST /api/v1/auth/logout` | 204 | 세션 삭제 |

- `campusId`는 지점이 없는 계정에서 `null`이다(필드를 빼지 않는다).
- 초기 설계에 있던 토큰 재발급 경로(`/api/v1/auth/refresh`)는 만들지 않는다. 세션 방식에는 재발급이 없다. ADR-0013의 공개 경로 목록도 이에 맞춰 `/api/v1/auth/csrf`로 바꿨다.

**CSRF와 CORS**

- CSRF 토큰은 쿠키 `XSRF-TOKEN`으로 주고 요청 헤더 `X-XSRF-TOKEN`으로 받는다. 이 쿠키는 프론트가 읽어야 하므로 `HttpOnly`가 아니다.
- 프론트는 앱을 시작할 때 `GET /api/v1/auth/csrf`를 한 번 호출한다. 로그인과 로그아웃 요청에도 토큰이 필요하다. 로그인해도 토큰은 바뀌지 않는다.
- 토큰 없는 변경 요청은 로그인 여부와 무관하게 403이고, 토큰은 있는데 세션이 없으면 401이다(ADR-0014).
- 프론트와 백엔드는 호스트가 다르다. 허용 출처(`jey.auth.allowed-origins`)가 아닌 곳에서 온 요청은 서버가 거부한다(`/api/**`). CSRF 쿠키는 프론트가 읽을 수 있게 공통 상위 도메인(`jey.auth.cookie-domain`)에 둔다. 세션 쿠키는 API 호스트 전용이다.

**설정 검사**

- 인증 설정이 잘못되면 서버가 뜨지 않는다.
  - 허용 출처: 형식이 `http(s)://호스트[:포트]`가 아니거나, `*`이거나, 환경변수가 빠진 경우. 운영에서는 비어 있는 경우도 포함한다.
  - 세션 시간: 만료 시간이나 최대 유지 시간이 1분보다 짧은 경우(단위를 빼먹은 값), 최대 유지 시간이 만료 시간보다 짧은 경우.
  - 첫 관리자(계정이 하나도 없을 때만 검사한다): 아이디와 비밀번호 중 하나만 있는 경우, 비밀번호가 10자보다 짧거나 72바이트를 넘는 경우, 운영인데 설정이 없는 경우. 계정이 이미 있으면 첫 관리자 설정은 읽지 않는다.
- 쿠키 도메인의 형식은 검사하지 않는다.

**공통 기록**

- 모든 엔티티는 `BaseEntity`를 상속해 생성 시각, 수정 시각, 작성자(계정 ID)를 남긴다. 시각은 애플리케이션 시계에서 얻고(ADR-0017), 로그인 없이 일어난 일은 작성자를 비워 둔다.

## 근거
- JWT의 장점은 서버가 상태를 들지 않아도 된다는 것인데, 즉시 차단을 하려면 결국 서버에 상태(리프레시 토큰, 차단 목록)를 둬야 한다. 세션 방식도 즉시 차단에 계정별 세션 색인이 필요하지만, Spring Session이 제공하는 기능이라 직접 만들 것이 적다.
- 서버가 한 대이고 Redis가 이미 있어서 추가 인프라가 없다. 서버를 늘려도 Redis를 공유하면 그대로 동작한다.
- 하루 종일 켜 둔 화면에서는 "쓰는 동안 연장"이 자연스럽다. JWT로 같은 경험을 주려면 재발급과 실패한 요청의 재시도를 프론트에 만들어야 한다.
- 프론트는 어느 방식이든 httpOnly 쿠키와 CSRF 헤더만 다룬다. 세션 방식에서는 재발급 처리가 필요 없어 더 단순하다.
- 로그인 실패의 응답이나 걸리는 시간이 이유에 따라 다르면, 그것만으로 어떤 아이디가 존재하는지, 어떤 계정이 비활성인지 알아낼 수 있다.
- DB 장애를 "비밀번호가 틀렸다"로 응답하면 장애가 로그인 실패로 보이고 원인도 남지 않는다.
- 지점 없는 직원 계정을 허용하면, 지점이 없는 계정을 "전 지점"으로 다루는 곳에서 전 지점 권한이 되어 버린다.
- 저장소가 공개라 운영 관리자의 비밀번호를 마이그레이션 파일에 둘 수 없다.
- 설정이 잘못된 채로 뜬 서버는 겉으로는 정상이라 문제를 늦게 알게 된다. 뜰 때 실패하는 편이 낫다.

## 포기한 것
- 요청마다 Redis를 조회한다. Redis가 내려가면 로그인한 사용자도 요청할 수 없다.
- 세션은 Java 직렬화로 저장된다. 세션에 넣는 타입(`AuthenticatedUser`, `UserRole`)의 이름이나 필드 타입을 바꾸면 기존 세션을 읽지 못하고, 그런 세션은 끊어서 다시 로그인하게 한다. 필드를 추가하면 기존 세션에서는 그 값이 비어서 읽힌다(참조 타입은 `null`, 기본 타입은 0/false). 생성자가 빈 값을 거부하는 필드라면 그 세션도 읽지 못한 것으로 처리된다.
- 메모리 부족이나 클래스 누락 같은 JVM 오류로 세션을 읽지 못한 경우는 "읽지 못한 세션"으로 취급하지 않고 오류로 응답한다. 서버의 문제를 전원 로그아웃으로 가리지 않기 위해서다.
- 세션에 든 사용자 정보는 로그인 시점의 값이다. 세션을 끊지 않으면 최대 유지 시간까지 예전 값으로 동작한다.
- 다른 서비스나 외부 시스템이 사용자를 직접 검증할 수 없다. 이 서버에 물어봐야 한다.
- 비활성 계정으로 로그인하려는 사람도 "아이디 또는 비밀번호가 올바르지 않습니다"만 보게 된다.
- 데스크 PC는 마지막 요청 후 12시간, 로그인 후 최대 16시간까지 로그인된 채로 남는다.
- 차단과 동시에 진행 중이던 로그인을 완전히 막지는 않는다(위 "즉시 차단"). 완전히 막으려면 요청마다 계정의 차단 시각을 확인해야 하는데, 그 비용을 들이지 않기로 했다.
- 아이디에 한글이나 대문자를 쓸 수 없다.
- CSRF 쿠키를 상위 도메인에 두면 같은 상위 도메인의 다른 서브도메인도 그 쿠키를 읽고 쓸 수 있다.

## 재검토 조건
- 다른 서비스가 사용자 인증을 직접 검증해야 할 때 (알림 서비스 분리, 외부 공개 API)
- 브라우저가 아닌 클라이언트(모바일 앱 등)가 생길 때
- 지점에 데스크 직원이 여러 명이 되어 한 PC를 번갈아 쓰게 될 때 (만료 시간, 교대 시 로그아웃)
- 학부모 로그인을 도입할 때 (소셜 로그인, 휴대폰 인증)
- 같은 상위 도메인에 신뢰할 수 없는 서브도메인이 생길 때 (CSRF 쿠키의 도메인)
- 계정 차단이 잦아지거나 차단 직후의 틈이 문제가 될 때 (요청마다 차단 시각 확인)
