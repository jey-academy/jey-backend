# ADR-0019: 인증은 서버 세션으로

- 상태: 채택
- 날짜: 2026-10-10

## 배경
직원, 관리자, 연계 학원이 아이디와 비밀번호로 로그인해야 한다. 초기 설계는 JWT를 httpOnly 쿠키에 담는 방식이었는데, 구현에 앞서 다시 검토했다.

이 서비스의 조건은 이렇다.
- 서버는 한 대짜리 모놀리스이고 Redis를 이미 쓴다.
- 퇴사한 직원이나 계약이 끝난 연계 학원의 계정은 즉시 막을 수 있어야 한다.
- 데스크 직원은 화면을 하루 종일 켜 두고 쓴다.
- 프론트는 브라우저에서 도는 웹앱 하나이고, 인증 정보를 직접 다루지 않는다(httpOnly 쿠키).

## 선택지
1. **JWT(액세스 + 리프레시)를 쿠키로** — 서버가 상태를 들지 않아도 토큰만으로 인증. 서버 종류가 여럿일 때 유리 / 발급한 토큰은 만료 전까지 유효해서 즉시 차단하려면 리프레시 토큰 저장, 교체, 차단 목록을 직접 만들어야 함. 프론트에도 재발급 처리가 필요
2. **서버 세션(Redis 저장)** — 세션을 지우면 즉시 로그아웃. 쓰는 동안 자동 연장. Spring Security 기본 기능으로 구현 / 요청마다 Redis 조회. 다른 서비스가 사용자를 직접 검증하기 어려움

## 결정
2번을 채택한다.

**방식**

- 인증 상태는 서버 세션에 두고 Redis에 저장한다(Spring Session). 브라우저에는 세션 쿠키만 준다.
- 새 의존성: `spring-boot-starter-session-data-redis` (Spring Boot가 버전을 관리).
- 세션 쿠키 `SESSION`: `HttpOnly`, `SameSite=Lax`, 운영에서는 `Secure`. 속성은 코드에서 직접 정한다.
- 로그인하면 세션 ID를 바꾼다(세션 고정 공격 방지).
- 인증 없는 요청은 세션을 만들지 않는다.
- 세션은 마지막 요청으로부터 `STAFF` 12시간, `ADMIN`·`PARTNER` 2시간 뒤에 만료된다(설정값). 데스크 직원은 지점마다 한 명이고 화면을 하루 종일 켜 둔다. 12시간이면 운영 시간 내내 유지되고 밤사이에 만료된다. 권한이 큰 관리자와 학원 밖에서 접속하는 연계 학원은 짧게 둔다.

**계정과 로그인**

- 1차 로그인 대상은 직원(`STAFF`), 관리자(`ADMIN`), 연계 학원(`PARTNER`)이다. 학부모는 로그인 없이 링크로 패스를 연다.
- 비밀번호는 BCrypt로 해시하고, 해시 앞에 알고리즘 이름을 붙여 저장한다(`{bcrypt}…`).
- 로그인 실패는 이유를 구분하지 않는다. 아이디가 없든, 비밀번호가 틀렸든, 비활성 계정이든 401 `AUTH_INVALID_CREDENTIALS`와 같은 문구다. 원인은 서버 로그에만 남기고, 입력한 아이디는 로그에 남기지 않는다.
- 에러 코드 접두사는 `AUTH_`다. `core`는 API 경로(ADR-0013)와 마찬가지로 모듈 이름 대신 하위 영역 이름을 쓴다.
- 계정이 하나도 없을 때는 실행 환경의 설정값(`jey.auth.initial-admin`)으로 관리자 한 명을 만든다. 계정이 이미 있으면 아무것도 하지 않는다.

**API**

| 주소 | 동작 |
|---|---|
| `GET /api/v1/auth/csrf` | CSRF 토큰 쿠키 발급 (공개) |
| `POST /api/v1/auth/login` | `{ loginId, password }`로 로그인. 사용자 정보와 세션 쿠키 응답 |
| `GET /api/v1/auth/me` | 로그인한 사용자의 ID, 아이디, 이름, 역할, 소속 지점 |
| `POST /api/v1/auth/logout` | 세션 삭제 |

**CSRF와 CORS**

- CSRF 토큰은 쿠키 `XSRF-TOKEN`으로 주고 요청 헤더 `X-XSRF-TOKEN`으로 받는다. 이 쿠키는 프론트가 읽어야 하므로 `HttpOnly`가 아니다.
- 프론트는 앱을 시작할 때 `GET /api/v1/auth/csrf`를 한 번 호출한다. 로그인과 로그아웃 요청에도 토큰이 필요하다. 로그인해도 토큰은 바뀌지 않는다.
- 프론트와 백엔드는 같은 상위 도메인의 서브도메인으로 나뉜다. 허용 출처(`jey.auth.allowed-origins`)만 쿠키를 실은 요청을 보낼 수 있고, CSRF 쿠키의 도메인(`jey.auth.cookie-domain`)은 설정값이다.

**공통 기록**

- 모든 엔티티는 `BaseEntity`를 상속해 생성 시각, 수정 시각, 작성자(계정 ID)를 남긴다. 시각은 애플리케이션 시계에서 얻고(ADR-0017), 로그인 없이 일어난 일은 작성자를 비워 둔다.

## 근거
- JWT의 장점은 서버가 상태를 들지 않아도 된다는 것인데, 즉시 차단을 하려면 결국 서버에 상태(리프레시 토큰, 차단 목록)를 둬야 한다. 그러면 세션보다 복잡한 세션이 된다.
- 서버가 한 대이고 Redis가 이미 있어서, 세션 방식이 추가로 요구하는 것이 없다. 서버를 늘려도 Redis를 공유하면 그대로 동작한다.
- 하루 종일 켜 둔 화면에서는 "쓰는 동안 연장"이 자연스럽다. JWT로 같은 경험을 주려면 재발급과 실패한 요청의 재시도를 프론트에 만들어야 한다.
- 프론트는 어느 방식이든 httpOnly 쿠키와 CSRF 헤더만 다룬다. 세션 방식에서는 재발급 처리가 필요 없어 더 단순하다.
- 로그인 실패 응답이 이유에 따라 다르면, 응답만으로 어떤 아이디가 존재하는지 알아낼 수 있다.
- 저장소가 공개라 첫 관리자의 비밀번호를 마이그레이션 파일에 둘 수 없다.

## 포기한 것
- 요청마다 Redis를 조회한다. Redis가 내려가면 로그인한 사용자도 요청할 수 없다.
- 세션은 Java 직렬화로 저장된다. 세션에 넣는 타입(`AuthenticatedUser`)의 구조를 바꾸면 기존 세션을 읽지 못해 사용자가 다시 로그인해야 한다.
- 다른 서비스나 외부 시스템이 사용자를 직접 검증할 수 없다. 이 서버에 물어봐야 한다.
- 비활성 계정으로 로그인하려는 사람도 "아이디 또는 비밀번호가 올바르지 않습니다"만 보게 된다.
- 데스크 PC는 로그인된 채로 최대 12시간 열려 있다.

## 재검토 조건
- 다른 서비스가 사용자 인증을 직접 검증해야 할 때 (알림 서비스 분리, 외부 공개 API)
- 브라우저가 아닌 클라이언트(모바일 앱 등)가 생길 때
- 지점에 데스크 직원이 여러 명이 되어 한 PC를 번갈아 쓰게 될 때 (만료 시간, 교대 시 로그아웃)
- 학부모 로그인을 도입할 때 (소셜 로그인, 휴대폰 인증)
