# ADR-0020: 로그인 시도 제한은 Redis 카운터로

- 상태: 채택
- 날짜: 2026-10-11

## 배경
로그인 API는 인증 없이 열려 있다(ADR-0019). 시도 횟수에 제한이 없으면 비밀번호를 계속 바꿔 가며 넣는 공격을 막을 수 없다.
제한을 어떻게 거느냐에 따라 다른 문제가 생긴다. 아이디만으로 세면 누군가 일부러 틀려서 남의 계정을 잠글 수 있다. 데스크 직원은 지점당 한 명이라, 그 계정이 잠기면 지점의 업무가 멈춘다.
초기 설계는 요청 제한에 토큰 버킷 라이브러리(Bucket4j)를 쓰기로 했다.

## 선택지
**도구**
1. Bucket4j + Redis — 초당 요청 수 같은 속도 제한에 맞는 도구 / 새 의존성, "실패만 세고 성공하면 지운다"는 로그인의 요구와 모양이 다름
2. Redis 카운터를 직접 — 증가와 만료 시간만 있으면 됨, 의존성 없음 / 속도 제한이 필요한 다른 기능에는 그대로 쓰기 어려움

**무엇을 기준으로 세는가**
1. 아이디 — 여러 곳에서 나눠 시도해도 막힘 / 남의 계정을 일부러 잠글 수 있음
2. IP — 계정을 잠글 수 없음 / 같은 IP를 쓰는 사람끼리 한도를 나눠 씀, 한도를 넉넉히 둬야 해서 한 계정을 노리는 시도에 느슨함
3. 아이디 + IP와 IP 두 가지 — 한 곳에서 오는 시도를 두 방향으로 막고 계정은 잠기지 않음 / 여러 곳에서 나눠 오는 시도는 못 막음

## 결정
도구는 2번, 기준은 3번을 채택한다.

**세는 방법**
- 두 가지를 센다.

| 기준 | 기본 한도 | 막는 것 |
|---|---|---|
| 아이디 + IP | 15분에 5회 | 한 곳에서 한 계정에 비밀번호를 바꿔 가며 넣는 시도 |
| IP | 15분에 30회 | 한 곳에서 아이디를 바꿔 가며 넣는 시도 |

- 한도와 기간은 설정값이다(`jey.auth.login-attempt-limit`). 값이 잘못되면 서버가 뜨지 않는다.
- 횟수는 비밀번호를 검증하기 **전에** 올리고, 로그인에 성공하면 되돌린다(아이디 + IP 횟수는 지우고, IP 횟수는 1을 뺀다). 결과적으로 실패만 남는다.
- 틀린 비밀번호, 없는 아이디, 형식이 틀린 아이디, 비활성 계정이 모두 실패다. 비활성 계정에 맞는 비밀번호를 넣은 것도 실패다.
- 기간은 첫 실패부터 센다. 막힌 뒤에 계속 시도해도 풀리는 시각은 밀리지 않는다.
- 증가와 만료 시간 지정은 Redis 스크립트 하나로 한다.
- Redis 키에는 아이디 원문 대신 해시를 넣는다. 로그에는 IP만 남기고 아이디는 남기지 않는다.

**응답**
- 한도를 넘으면 비밀번호를 검증하지 않고 429 `AUTH_TOO_MANY_ATTEMPTS`로 응답한다. 맞는 비밀번호여도 같다.
- `Retry-After` 헤더에 다시 시도할 수 있을 때까지 남은 시간(초, 올림)을 싣는다. 프론트가 읽을 수 있게 CORS 노출 헤더에 넣는다.
- 이미 로그인한 세션은 영향을 받지 않는다.

**IP**
- 서버가 본 요청 주소를 쓴다. 운영에서는 프록시가 전달 헤더로 넘겨준 주소다.

## 근거
- 로그인에 필요한 것은 "정해진 기간의 실패 횟수"다. 토큰 버킷은 요청 속도를 고르게 하는 도구라, 성공하면 지우는 동작을 얹으면 오히려 복잡해진다. Redis의 증가와 만료 시간이면 충분하고 이미 쓰는 Redis 외에 필요한 것이 없다.
- 해시 계산은 느리다. "검증하고 틀렸으면 증가"로 만들면 동시에 보낸 요청이 모두 확인을 통과해서 한도를 넘는다. 먼저 올리면 Redis의 증가가 원자적이라 한도가 정확히 지켜진다.
- 증가와 만료 시간 지정을 따로 하면 그 사이에 연결이 끊겼을 때 만료 시간 없는 키가 남아 그 아이디나 IP가 영원히 잠긴다.
- 없는 아이디도 똑같이 세야 응답으로 계정이 있는지 드러나지 않는다.
- 한도를 넘은 뒤에 맞는 비밀번호를 받아 주면, 막힌 동안에도 비밀번호를 계속 확인할 수 있다.
- 아이디 칸에 비밀번호를 잘못 넣는 일이 흔하다. 그 값이 Redis 키나 로그에 그대로 남으면 안 된다.

## 포기한 것
- 여러 IP에서 한 계정을 나눠 시도하는 공격은 막지 못한다. IP마다 5회씩 시도할 수 있다. 프록시의 요청 제한과 비밀번호 길이로 버틴다.
- 같은 IP를 쓰는 사람끼리 IP 한도를 나눠 쓴다. 같은 공유기 뒤에서 한 사람이 30번 틀리면 다른 사람도 그 기간 동안 새로 로그인할 수 없다.
- 프록시가 요청 주소를 넘겨주지 않으면 모든 요청이 프록시의 주소로 보여 전체가 한도 하나를 나눠 쓴다. 프록시 설정이 맞아야 한다.
- 막힌 뒤의 시도도 IP 횟수에 더해진다. 한 계정이 막힌 채로 계속 시도하면 그 IP 전체가 막힐 수 있다.
- Redis가 응답하지 않으면 로그인할 수 없다. 세션도 Redis에 있으므로 달라지는 것은 없다.
- 반복해서 막혀도 잠금 시간이 늘어나지 않는다. 계정을 잠그거나 관리자에게 알리는 기능도 없다.
- 요청 속도 제한이 필요한 기능(패스 조회 등)에는 이 카운터를 그대로 쓰지 않는다.

## 재검토 조건
- 패스 조회처럼 요청 속도를 제한해야 하는 기능을 만들 때 (토큰 버킷 라이브러리 도입)
- 여러 IP에서 나눠 오는 시도가 로그에서 보일 때 (아이디 기준 한도, 잠금 시간 늘리기, 알림)
- 학부모 로그인처럼 같은 IP에서 많은 사람이 로그인하게 될 때 (IP 한도)
- 서버가 여러 대가 되거나 프록시 구성이 바뀔 때 (요청 주소를 읽는 방법)
