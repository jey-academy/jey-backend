# ADR-0022: API 명세 파일을 프론트와의 계약으로 둔다

- 상태: 채택
- 날짜: 2026-10-11

## 배경
프론트는 API 타입을 손으로 쓰지 않고 OpenAPI 명세에서 생성한다. 지금까지는 로컬에서 실행 중인 서버의 명세 주소를 읽어 생성했다.
이 방식에는 빈틈이 셋 있다.
- 서버를 띄워야만 타입을 만들 수 있다. 어느 시점의 명세로 만든 타입인지도 남지 않는다.
- 응답 필드를 바꿔도 백엔드의 PR에는 드러나지 않는다. 프론트는 타입을 다시 만들 때까지 모른다.
- 타입만 봐서는 알 수 없는 것(할인율이 퍼센트인지 비율인지 등)을 전할 곳이 PR 본문뿐이다.

백엔드와 프론트는 저장소가 다르다. 두 저장소가 같은 것을 보려면 계약이 어느 한쪽의 실행 상태가 아니라 파일로 있어야 한다.

## 선택지
1. 명세 파일을 백엔드 저장소에 커밋하고, 현재 명세와 다르면 실패하는 테스트를 둔다 — 새 도구가 없음, 변경이 PR의 diff로 보임 / 명세가 실제 응답과 같은지는 확인하지 않음
2. 소비자 주도 계약 테스트(프론트가 기대하는 요청·응답을 적고 백엔드가 검증) — 실제 응답까지 검증 / 도구와 중계 저장소가 필요, 프론트 화면이 생기기 전에는 적을 기대가 없음
3. 명세를 버전을 붙여 패키지로 배포 — 버전이 명확함 / 배포 절차가 생김, 저장소가 둘뿐인 지금은 얻는 것이 적음

## 결정
1번을 채택한다.

- 명세는 `docs/api/openapi.json`에 둔다. 서버가 내보내는 명세에서 요청 주소에 따라 달라지는 값(서버 주소)을 빼고, 키를 정렬해 저장한다.
- 테스트가 현재 명세와 이 파일을 구조로 비교한다. 다르면 달라진 경로와 스키마의 이름, 그리고 파일을 다시 쓰는 명령을 알려 주며 실패한다.
- API를 의도해서 바꿨으면 파일을 다시 써서 같은 PR에 커밋한다. 파일을 다시 쓰는 방법은 하나다: `./gradlew test --tests "*ApiSpecTest" -PupdateApiSpec`. CI는 이 옵션을 쓰지 않고 비교만 한다.
- 프론트는 이 파일에서 타입을 생성한다. 실행 중인 서버를 읽지 않는다.
- 타입만 봐서는 알 수 없는 것은 명세의 설명으로 적는다. 생성된 타입에 주석으로 따라간다. 대상은 값의 표현(금액의 단위, 할인율이 비율이라는 것), 값이 없을 수 있는 필드, 통째로 바꾸는 수정 요청이다.
- 응답 필드는 항상 있는지를 명세에 표시한다. 표시하지 않으면 생성된 타입에서 모든 필드가 "없을 수 있음"이 된다.
- 테스트용 컨트롤러는 명세에서 뺀다. 명세에 테스트 전용 경로가 없는지도 테스트로 확인한다.

## 근거
- 계약의 변경이 리뷰 대상이 된다. 응답 필드 하나를 지우면 명세 파일의 diff에 그 줄이 보이고, 의도하지 않은 변경이면 테스트가 먼저 막는다.
- 지금 쓰는 명세 생성 기능의 출력을 비교할 뿐이라 새 의존성이 없다.
- 프론트에 API를 부르는 화면이 아직 없다. 소비자가 기대를 적는 방식은 적을 기대가 생긴 뒤에 검토해도 늦지 않다.

## 포기한 것
- 명세가 실제 응답과 같은지는 이 장치가 확인하지 않는다. 명세는 코드에서 자동으로 만들어지므로 대체로 맞지만, 직렬화 설정이나 수동으로 쓴 응답은 어긋날 수 있다. 각 API의 응답 모양은 그 API의 테스트가 확인한다.
- 각 API가 어떤 에러 코드로 답하는지는 명세에 없다. 에러 응답의 모양(ADR-0014)은 공통이고, 코드 값은 PR에서 따로 알린다.
- 설명과 "항상 있음" 표시는 손으로 적는다. 빠뜨려도 테스트가 잡지 못한다.
- 프론트가 새 명세로 타입을 다시 만드는 일은 프론트 저장소의 몫이다. 백엔드가 바뀐 뒤 프론트가 낡은 타입으로 남는 것은 프론트 쪽 자동화로 막는다.
- API를 바꾸는 PR마다 파일을 다시 쓰는 단계가 하나 늘어난다.

## 재검토 조건
- 명세와 실제 응답이 어긋나 프론트에서 오류가 난 경우가 생길 때 → 응답을 명세로 검증하는 테스트나 소비자 주도 계약 테스트 검토
- 명세를 읽는 쪽이 프론트 하나가 아니게 될 때(외부 공개 API, 별도 서비스) → 버전을 붙인 배포 검토
- 에러 코드를 프론트가 타입으로 받아야 할 때 → 명세에 에러 코드를 싣는 방법 검토
