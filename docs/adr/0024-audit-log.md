# ADR-0024: 감사 로그는 직접 기록과 이벤트 구독 두 길로 받고, 거부된 시도는 따로 커밋한다

- 상태: 채택
- 날짜: 2026-10-11

## 배경
누가 언제 무엇을 했는지 남는 기록이 필요하다. 쓰임은 세 가지다.

- 문제가 생겼을 때 누가 무엇을 바꿨는지 되짚는다.
- 가린 전화번호를 대입으로 알아내는 시도(ADR-0023)처럼, 한 번은 정상이지만 되풀이하면 이상한 행동을 찾는다.
- 전체 번호 보기처럼 "본 사실을 남긴다"가 조건인 기능의 기록 장치가 된다.

기록할 일은 두 종류다. 기초 모듈 안에서 일어나는 일(학생·학부모 변경)과 다른 모듈에서 일어나는 일(패스 사용, 결제)이다.
기초 모듈은 다른 모듈에 의존하지 않으므로(ADR-0012) 다른 모듈의 타입을 알 수 없다.

## 선택지
**기록을 받는 길**
1. 창구 하나를 모든 모듈이 직접 부른다 — 단순함, 같은 트랜잭션에 적을 수 있음 / 모든 기능이 기록 호출을 빠뜨리지 않아야 함, 사건을 이미 이벤트로 내는 모듈은 같은 사실을 두 번 적게 됨
2. 도메인 이벤트만 구독한다 — 기능 코드가 기록을 몰라도 됨, 빠뜨릴 수 없음 / 이벤트가 없는 일은 기록할 수 없음, 거부된 요청은 이벤트가 나가지 않음
3. 둘 다 둔다 — 이벤트가 있는 일은 자동으로, 없는 일은 직접 / 길이 둘이라 어느 쪽으로 들어온 기록인지 알아야 함

**거부된 요청의 기록**
1. 요청과 같은 트랜잭션에 적는다 — 요청이 실패하면 기록도 롤백됨
2. 따로 커밋한다 — 요청이 실패해도 남음 / 연결을 하나 더 씀, 성공한 일에 쓰면 "했다"는 기록만 남고 실제는 롤백될 수 있음
3. 성공한 일은 같은 트랜잭션에, 거부된 시도는 따로 — 둘 다 실제와 어긋나지 않음 / 부르는 쪽이 둘 중 맞는 것을 골라야 함

**이벤트로 들어온 기록의 행위자**
1. 리스너가 로그인 정보에서 읽는다 — 리스너는 요청과 다른 스레드에서 돌아 읽을 수 없음
2. 이벤트마다 내용에 넣는다 — 감사 로그가 이벤트마다 다른 필드 이름을 알아야 함
3. 이벤트 봉투에 넣는다 — 모든 이벤트가 같은 자리에 가짐 / 봉투가 바뀜

## 결정
받는 길은 3번, 거부된 요청은 3번, 행위자는 3번을 채택한다.

**기록의 모양**
- 한 줄에 일어난 시각, 행위자(계정 ID), 행위, 대상(종류와 ID), 지점, 상세를 적는다.
- 행위 이름은 이벤트 이름과 같은 형식 `{모듈}.{사건}`이다. 한 번 쓴 이름은 바꾸지 않는다.
- 기록은 추가만 한다. 고치거나 지우는 기능이 없다.
- 개인정보(이름, 전화번호)를 싣지 않는다. ID만 싣는다.

**직접 적는 길**
- 창구는 두 가지 방법을 준다.
  - 성공한 일: 부르는 쪽의 트랜잭션에 같이 적는다. 그 일이 커밋돼야 기록도 남고, 기록하지 못하면 그 일도 실패한다.
  - 거부된 시도: 따로 커밋한다. 그 뒤에 요청이 예외로 끝나도 남는다.
- 행위자는 부르는 쪽이 넘기지 않는다. 로그인 정보에서 읽는다. 로그인 없이 일어난 일은 비어 있다.
- 상세는 작은 JSON 객체다. 값은 숫자, 참·거짓, enum, 짧은 문자열만 된다.
- 상세의 문자열에 전화번호처럼 보이는 값이 있으면 기록하지 않고 예외를 던진다. 예외 문구에 그 값을 싣지 않는다.

**이벤트로 받는 길**
- 모든 도메인 이벤트를 공통 봉투 타입으로 구독한다(ADR-0016). 개별 이벤트 타입을 알지 않는다.
- 행위 = 이벤트 이름, 일어난 시각 = 이벤트의 발생 시각, 지점 = 봉투의 지점, 상세 = 이벤트의 내용(봉투 제외)이다.
- 행위자는 봉투의 `actorId`다. 이 결정으로 봉투에 `actorId`를 추가한다.
- 이벤트 ID에 유니크 키를 건다. 같은 이벤트가 다시 와도 한 줄만 남고, 이미 적힌 이벤트는 성공으로 끝낸다.
- 내용이 상세 크기를 넘으면 잘라 넣지 않고 내용 없이 표시(`truncated`)만 남긴다.
- 내용에 전화번호처럼 보이는 문자열이 있으면 내용 없이 표시(`redacted`)만 남기고 오류 로그를 남긴다.

**조회**
- 관리자만 조회한다. 행위자, 행위, 대상, 기간으로 거르고 최신순으로 준다.

## 근거
- 다른 모듈의 사건은 이미 이벤트로 나간다. 그것을 받아 적으면 그 모듈의 코드가 감사 로그를 몰라도 되고, 새 이벤트는 저절로 기록된다.
- 이벤트가 없는 일도 있다. 거부된 요청이 대표적이다. 이것까지 이벤트로 만들면 기록만을 위한 이벤트가 늘어난다.
- 거부된 요청은 예외로 끝나 롤백된다. 같은 트랜잭션에 적으면 가장 남겨야 할 기록이 사라진다. 반대로 성공한 일을 따로 커밋하면 실제로는 롤백된 일이 "했다"로 남는다. 그래서 둘을 나눈다.
- 행위자를 부르는 쪽이 넘기게 하면 빠뜨리거나 틀린 값을 넣을 수 있다. 로그인 정보에서 읽으면 그럴 수 없다.
- 리스너는 실패하면 다시 실행된다. 저장한 뒤 완료 표시 전에 죽으면 같은 이벤트가 또 온다. 유니크 키 위반을 실패로 돌려주면 그 이벤트는 끝없이 다시 온다.
- 이벤트 길에서 규칙을 어긴 내용을 예외로 거부하면 그 이벤트도 끝없이 다시 온다. 그래서 거부하지 않고 내용만 뺀다. 직접 적는 길은 부르는 코드의 잘못을 바로 알려야 하므로 예외로 거부한다.
- 전화번호 검사를 규칙으로만 두면 언젠가 새어 들어간다. 기록은 오래 남고 지울 방법이 없다.

## 포기한 것
- 조회(읽기)는 기록하지 않는다. 누가 어떤 학생을 봤는지는 남지 않는다.
- 이벤트로 들어온 기록은 그 일보다 조금 늦게 보인다. 리스너가 커밋 뒤에 따로 돌기 때문이다. 리스너가 계속 실패하면 그 기록은 발행 기록에 남아 있다가 다시 보내질 때 적힌다.
- 이벤트로 들어온 기록에는 대상(종류와 ID)이 없다. 내용 안에 ID가 있지만 대상으로 거르는 조회에는 나오지 않는다.
- 기록의 위변조를 막는 장치(해시 사슬, 별도 저장소)가 없다. DB에 쓸 수 있는 사람은 기록을 고칠 수 있다.
- 보관 기간을 정하지 않았다. 지우는 작업이 없다.
- 거부된 시도의 기록은 연결을 하나 더 쓴다. 연결 풀이 바닥난 상황에서는 기록하려다 기다리게 된다.
- 전화번호 검사는 휴대전화 번호 모양만 본다. 이름이나 주소 같은 다른 개인정보는 걸러 내지 못한다. 문자열로 실린 값만 본다(ID는 숫자로 싣는다).
- 상세의 키는 행위마다 다르고 형식을 강제하지 않는다.

## 재검토 조건
- 조회(읽기)를 기록해야 할 때(개인정보 열람 기록 의무 등)
- 기록의 양이 조회를 느리게 할 때 → 보관 기간, 월별 분할
- 기록을 고칠 수 없다는 것을 증명해야 할 때 → 해시 사슬이나 추가 전용 저장소
- 이벤트로 들어온 기록을 대상으로 찾아야 할 때 → 이벤트가 대상을 알려 주는 공통 방법
