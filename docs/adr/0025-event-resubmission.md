# ADR-0025: 처리에 실패한 이벤트는 주기적으로 다시 보낸다

- 상태: 채택
- 날짜: 2026-10-11

## 배경
모듈끼리는 도메인 이벤트로 연결한다(ADR-0012, ADR-0016). 이벤트는 발행 기록(Event Publication Registry)에 저장되고, 리스너가 끝나면 완료로 표시된다.
리스너가 실패하면 그 이벤트는 미완료로 남는다. 남기만 하고 저절로 다시 실행되지는 않는다.

다시 보내는 것이 없으면, DB가 잠깐 끊기거나 연결을 얻지 못한 사이의 이벤트는 처리되지 않은 채로 남는다.
업무는 이미 커밋됐고 응답도 성공이라 아무도 모른다. 감사 로그라면 그 한 줄이 빠지고, 뒤에 올 패스 사용이나 결제의 후속 처리도 같은 식으로 빠진다.

## 선택지
1. 다시 보내지 않고 미완료 건을 사람이 본다 — 구현이 없음 / 빠진 것을 알아채야 하고 손으로 다시 보내야 함
2. 서버가 시작할 때만 다시 보낸다 — 설정 하나 / 서버가 오래 떠 있으면 그동안 실패한 것이 계속 남음
3. 주기적으로 다시 보낸다 — 실패가 저절로 메워짐 / 주기 작업이 하나 생김, 리스너가 같은 이벤트를 두 번 받을 수 있음
4. 메시지 브로커의 재시도에 맡긴다 — 재시도와 지연, 실패 보관함을 브로커가 해 줌 / 브로커를 도입해야 함

## 결정
2번과 3번을 함께 쓴다.

- 서버가 시작할 때 미완료 이벤트를 다시 보낸다.
- 주기 작업이 발행된 지 일정 시간이 지나도록 끝나지 않은 이벤트를 다시 보낸다. 간격과 기준 시간은 설정값이다(기본 1분마다, 5분 지난 것).
- 방금 발행돼 아직 처리 중인 이벤트는 다시 보내지 않는다. 기준 시간이 그것을 가른다.
- 다시 보내는 일 자체가 실패하면 로그를 남기고 다음 주기에 다시 한다.
- 모든 리스너는 멱등이어야 한다. 같은 이벤트를 다시 받아도 결과가 같아야 한다.

## 근거
- 이벤트로 연결한 이유가 "후속 처리의 실패가 본 작업을 되돌리지 않게"였다. 그러려면 실패한 후속 처리가 언젠가 다시 실행돼야 한다. 다시 보내는 것이 없으면 실패가 누락이 된다.
- 다시 보낼 때는 발행 기록에서 되살린 이벤트가 같은 ID로 도착한다. 리스너가 그 ID나 업무 키로 중복을 가릴 수 있다.
- 리스너가 처리를 끝내고 완료 표시 전에 죽은 경우에도 이벤트는 다시 온다. 그래서 멱등은 선택이 아니다.
- 브로커는 알림 발송을 붙일 때 도입하기로 했다. 그 전에는 발행 기록과 주기 작업으로 충분하다.

## 포기한 것
- 몇 번 실패하면 그만둔다는 한도가 없다. 영영 처리할 수 없는 이벤트는 주기마다 다시 실패한다. 그런 이벤트가 생기지 않게 리스너가 받는 쪽에서 막는다(예: 내용을 싣지 못하면 내용 없이 적는다 — ADR-0024).
- 실패한 이벤트를 따로 모아 두는 곳(실패 보관함)이 없다. 미완료 건은 발행 기록에서 직접 본다.
- 미완료 건수를 보여 주는 지표나 화면이 없다.
- 다시 보낼 때 간격을 늘려 가지 않는다. 주기는 고정이다.
- 처리 순서를 보장하지 않는다. 다시 보낸 이벤트는 그 뒤에 발행된 이벤트보다 늦게 처리될 수 있다.
- 서버가 여러 대면 각 서버가 같은 미완료 건을 다시 보낸다. 지금은 한 대다.
- 완료된 발행 기록을 지우는 작업이 없다. 기록이 계속 쌓인다.

## 재검토 조건
- 서버가 여러 대가 될 때 → 한 대만 다시 보내게 하거나 잠금
- 같은 이벤트가 계속 실패하는 것이 보일 때 → 실패 횟수 한도와 실패 보관함
- 처리 순서가 중요한 이벤트가 생길 때
- 브로커를 도입할 때 → 재시도를 브로커로 옮김
- 발행 기록이 커져 조회가 느려질 때 → 완료된 기록 정리
