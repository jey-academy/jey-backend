# ADR-0027: 부작용 있는 POST는 멱등 키로 한 번만 실행한다

- 상태: 채택
- 날짜: 2026-10-12

## 배경
요청은 서버에 도착해 처리됐는데 응답이 화면에 돌아오지 못하는 경우가 있다(연결이 끊김, 응답이 늦어 다시 누름, 자동 재시도).
화면은 됐는지 안 됐는지 모르므로 다시 보낼 수밖에 없고, 서버는 그것이 새 요청인지 아까의 요청인지 구분하지 못해 한 번 더 실행한다.

지금 있는 기능에서는 반이나 할인 유형이 둘씩 생기는 정도다. 학생 등록은 "같은 이름의 학생" 확인이 우연히 막지만, 화면은 409를 받을 뿐 등록됐는지는 알지 못한다.
뒤에 올 패스 사용과 결제는 두 번 실행되면 안 되고, 화면이 다시 보냈을 때 처음의 결과를 정확히 알아야 한다.

## 선택지
**무엇으로 같은 요청임을 아는가**
1. 업무 유니크 키만 쓴다(같은 이름, 같은 패스) — 장치가 없음 / 기능마다 따로 만들어야 하고, 다시 보낸 쪽은 거부만 받을 뿐 처음의 결과를 받지 못함. 유니크할 것이 없는 자료(반)는 막지 못함
2. 화면이 시도마다 키를 만들어 보낸다 — 모든 POST에 같은 방식, 다시 보낸 쪽이 처음의 응답을 그대로 받음 / 화면이 키를 관리해야 함, 서버에 응답을 보관해야 함

**응답을 어디에 보관하는가**
1. DB 테이블 — 업무와 같은 트랜잭션에 넣을 수 있음, 사라지지 않음 / 요청마다 한 줄, 지우는 작업이 필요함, 컨트롤러 밖에서 응답 본문을 트랜잭션에 넣기 어려움
2. Redis — 만료가 저절로 됨, 세션과 횟수 한도가 이미 쓰고 있음 / 비워지면 보관한 응답이 사라짐, 업무의 커밋과 따로 저장됨

**어디에서 처리하는가**
1. 컨트롤러 메서드마다 — 눈에 보임 / 빠뜨리기 쉽고 같은 코드가 되풀이됨
2. 필터 하나 + 메서드의 표시 — 응답을 바이트 그대로 보관할 수 있음, 오류 응답도 같은 길로 지나감 / 필터가 컨트롤러를 미리 알아내야 함

## 결정
키는 2번, 보관은 2번, 처리는 2번으로 한다.

- 화면은 부작용이 있는 POST에 `Idempotency-Key` 헤더를 싣는다. 키는 한 번의 시도마다 하나다. 같은 시도를 다시 보낼 때는 같은 키를 쓰고, 값을 고쳐 다시 내는 것은 새 시도이므로 새 키를 쓴다.
- 키는 계정별로 본다. 다른 계정이 같은 키를 써도 서로의 응답을 받지 않는다. 그래서 로그인이 필요한 경로에만 쓴다.
- 처음 온 키는 "처리 중"으로 선점하고 일을 한다. 확인과 선점은 한 번에 한다.
- 같은 키가 다시 오면:

| 상황 | 응답 |
|---|---|
| 처음 요청이 끝났고 내용이 같다 | 일을 다시 하지 않고 보관한 응답을 그대로 돌려준다(상태, 본문 타입, 본문, 다시 돌려준 것이라는 표시 헤더) |
| 처음 요청이 아직 처리 중이다 | 기다리게 하지 않고 거부한다(409). 잠시 뒤 다시 보내면 결과를 받는다 |
| 내용(주소나 본문)이 다르다 | 거부한다(422) |

- 키가 필요한 경로에 키가 없거나 형식이 틀리면 거부한다(400). 키는 필수다.
- 끝난 요청의 응답은 24시간 보관한다(설정값). 성공(2xx)과 본문이 있는 거부(4xx)를 보관한다.
  - 서버 오류(5xx)는 보관하지 않는다. 일이 됐는지 모르는 답이고, 같은 키로 다시 시도할 수 있어야 한다.
  - 횟수 한도에 막힌 응답(429)도 보관하지 않는다. 보관하면 "잠시 후 다시"를 따른 요청이 같은 답을 받는다.
  - 다른 주소로 보내는 응답(3xx)은 보관하지 않는다. 헤더가 전부인 응답인데 헤더는 보관하지 않는다.
  - 너무 큰 응답은 보관하지 않는다.
- 보관하는 것은 상태와 본문 타입과 본문이다. 그 밖의 응답 헤더는 보관하지 않는다.
- "처리 중" 표시는 임대 시간(2분, 설정값, 10분 이하) 동안만 남는다. 처리하던 서버가 죽어도 그 뒤에는 같은 키로 다시 시도할 수 있다.
- 선점한 요청만 끝내거나 풀 수 있다. 임대가 끝나 다른 요청이 다시 선점한 뒤에 늦게 끝난 쪽이 그것을 덮지 못한다. 끝낸 선점은 다시 끝내거나 풀 수 없다.
- 키를 확인하지 못하면(저장소에 닿지 못함) 요청을 실행하지 않는다. 응답을 보관하지 못한 경우에는 응답을 그대로 내보내고 로그를 남긴다.
- 맞는 컨트롤러 메서드가 없는 요청(없는 경로, 지원하지 않는 메서드나 본문 타입)은 키를 보지 않고 넘긴다. 뒤에서 원래의 이유로 거절된다.
  그 밖의 이유로 컨트롤러를 알아내지 못하면 요청을 멈춘다. "키가 필요 없다"로 넘기면 장치가 조용히 꺼진다.
- 붙이는 메서드는 JSON 본문을 받거나 본문이 없고, 그 자리에서 응답하는 메서드다.
  폼과 파일 올리기로 온 요청은 거부한다(415). 비동기로 응답하는 메서드에 붙이면 응답을 보관하지 않고 실패시킨다.
- 다시 돌려주는 것은 접근 규칙(역할)을 확인하는 것보다 앞이다. 보관한 응답은 지금의 역할을 다시 묻지 않고 그 계정에 돌려준다.
- 필터가 거부하는 응답(400, 409, 415, 422)은 그 자리에서 쓴다. 다른 응답과 같은 형식이고, 앞의 필터가 붙이는 보안 헤더가 그대로 나간다.
- 모든 POST 메서드는 "키를 받는다" 또는 "받지 않는다(이유)"를 표시한다. 표시가 없으면 테스트가 실패한다.
  받지 않는 것: 로그인(계정을 알기 전이다), 로그아웃(다시 해도 결과가 같다), 전체 전화번호 보기(다시 보내면 한 번 더 본 것으로 센다 — ADR-0026).
- API 명세에는 필수 헤더로 싣는다(ADR-0022).
- 업무 규칙의 중복 확인(같은 이름의 학생 등)은 그대로 둔다. 키가 다른 두 요청은 이 장치가 막지 못한다.

## 근거
- 다시 보낸 쪽에 필요한 것은 "거부"가 아니라 "처음의 결과"다. 결제를 다시 보낸 화면은 결제됐는지를 알아야 한다. 업무 유니크 키는 중복을 막을 뿐 결과를 돌려주지 못한다.
- 응답을 바이트 그대로 보관하면 다시 만든 응답이 처음과 달라질 일이 없다(그사이 자료가 바뀌었어도 처음의 응답이 나간다).
- 거부(4xx)도 그 시도의 결과다. 보관하지 않으면 거부된 요청을 다시 보낼 때마다 다시 실행되고, 번호가 드러나는 거부처럼 횟수를 세는 것이 다시 세어진다.
- Redis는 세션과 횟수 한도에 이미 쓰고 있어 새로 들이는 것이 없다. 만료가 저절로 돼 지우는 작업이 필요 없다.
- 표시를 강제하지 않으면 새 POST를 만들 때 빠뜨려도 아무도 모른다. 다시 보낸 요청이 두 번 실행되는 것은 평소의 테스트로는 드러나지 않는다.
- 돈이 걸리지 않은 경로에서 먼저 써 보면, 결제에 붙이기 전에 경계 상황(동시 요청, 저장소 장애, 처리 중 종료)을 겪어 볼 수 있다.

## 포기한 것
- 응답의 보관과 업무의 커밋은 따로다. 일은 커밋됐는데 응답을 보관하지 못하면(저장소 장애, 그 사이의 서버 종료) 임대가 끝난 뒤 같은 키가 다시 실행된다. 이 경우는 업무 규칙이 막아야 한다. 결제는 결제 테이블의 유니크 키가 마지막으로 막는다.
- Redis가 비워지면 보관한 응답이 모두 사라진다. 그 뒤에 온 같은 키는 처음 온 키로 본다.
- 요청 하나가 임대 시간보다 오래 걸리면 같은 키의 요청이 겹쳐 실행될 수 있다.
- 키가 다른 중복(버튼을 두 번 눌러 키가 둘 생김, 두 화면에서 등록)은 막지 못한다. 화면이 버튼을 막고 업무 규칙이 막는다.
- 거부를 보관하므로, 거부의 원인이 사라진 뒤에도 같은 키로는 24시간 동안 같은 거부를 받는다. 화면은 새 시도에 새 키를 써야 한다.
- 서버 오류를 받은 요청을 같은 키로 다시 보내면 다시 실행된다. 처음 요청이 실제로는 반쯤 됐다면 업무 규칙이 막아야 한다.
- 내용이 같은지는 주소와 본문의 바이트로 본다. 뜻은 같고 표기만 다른 본문(공백, 필드 순서)은 다른 요청으로 본다.
  본문의 타입(`Content-Type`)은 보지 않는다. 타입이 틀려 거부된 요청을 타입만 고쳐 같은 키로 다시 보내면 처음의 거부를 받는다.
- 다시 돌려주는 응답에는 처음 응답의 헤더가 없다(상태, 본문 타입, 본문만 있다). 응답 헤더에 뜻을 싣는 경로(`Location`으로 만든 자료의 주소를 알림 등)에는 그대로 쓰지 못한다.
- 역할이나 지점이 바뀐 뒤에도 같은 키와 같은 내용으로는 바뀌기 전의 응답을 다시 받는다(보관 기간 동안).
  관리자일 때 만든 자료의 응답을 직원이 된 뒤 같은 키로 다시 받을 수 있고, 권한이 없어 받은 거부를 권한이 생긴 뒤 같은 키로 다시 받는다.
  받는 것은 그 계정이 이미 받았던 응답뿐이고, 일이 다시 실행되지는 않는다. 새 키로 보낸 요청은 지금의 역할대로 처리된다.
- 본문을 통째로 읽으므로 큰 요청과 폼·파일 올리기에는 쓰지 못한다. 비동기로 응답하는 메서드에도 쓰지 못한다.
- 계정 하나가 만들 수 있는 키의 수에는 한도가 없다. 키마다 응답 하나가 보관 기간 동안 저장소에 남는다.
- 보관한 응답에는 응답 본문이 그대로 들어간다(이름, 가린 전화번호). 전체 전화번호를 내주는 경로는 대상이 아니다.
- 저장소에 닿지 못하는 동안에는 키가 필요한 요청이 모두 실패한다.
- 로그인 없이 열린 경로에는 쓰지 못한다.
- PUT과 DELETE에는 적용하지 않는다. 지금의 것들은 다시 보내도 결과가 같거나 "없는 대상"으로 끝난다.

## 재검토 조건
- 결제를 붙일 때 → 결제 테이블의 유니크 키와 함께 쓰고, 결제 상태를 조회하는 길을 따로 둔다
- 응답 헤더에 뜻을 싣는 경로에 붙일 때 → 보관할 헤더를 정해 함께 보관
- 역할이나 지점이 바뀐 계정이 예전 응답을 다시 받는 것이 문제가 될 때(지점으로 묶은 수납·패스 자료) → 요청의 내용을 가리는 값에 역할과 지점을 넣어, 바뀐 뒤의 같은 키를 거부
- 폼이나 파일 올리기를 받는 부작용 요청이 생길 때 → 본문을 읽지 않고 가리는 방식을 따로 둠
- 로그인 없이 받는 부작용 요청이 생길 때(결제 대행사의 통지 등) → 그쪽이 주는 식별자로 따로 처리
- 임대 시간보다 오래 걸리는 요청이 생길 때 → 임대 연장이나 그 경로만 긴 임대
- 보관한 응답이 저장소를 많이 차지할 때 → 보관 기간 조정, 본문 대신 결과를 다시 읽어 만드는 방식
- 다시 보내면 결과가 달라지는 PUT·DELETE가 생길 때 → 같은 표시를 그 메서드에도 적용
