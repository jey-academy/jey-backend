# ADR-0028: 요청마다 ID를 정해 로그와 오류 응답에 싣는다

- 상태: 채택
- 날짜: 2026-10-12

## 배경
로그에는 요청을 구분하는 값이 없었다. 요청이 겹치면 어느 줄이 어느 요청의 것인지 가를 수 없고,
화면에서 본 오류를 서버 로그에서 찾으려면 시각과 경로로 짐작해야 했다.
이벤트 리스너는 요청을 처리한 스레드가 아닌 곳에서 돌기 때문에, 요청이 낸 이벤트의 처리 로그는 그 요청과 더욱 이어지지 않았다.

운영 로그는 모아서 찾아볼 것이므로, 사람이 읽는 글 형식보다 도구가 필드로 읽는 형식이 필요하다.

## 선택지
**무엇으로 요청을 묶는가**
1. 요청 ID 하나를 직접 정해 로그 문맥(MDC)에 넣는다 — 새로 들이는 것이 없음, 동작이 눈에 보임 / 서버 밖(다른 서비스, 메시지)으로 넘기는 것은 직접 만들어야 함
2. 분산 추적 도구를 쓴다(추적 ID와 구간 ID, 수집 서버) — 서비스 사이의 호출을 이어 봄 / 서버가 하나인 지금은 이어 볼 호출이 없고, 수집 서버를 운영해야 함

**들어온 ID를 믿는가**
1. 믿지 않고 항상 새로 만든다 — 값이 깨끗함 / 앞단의 프록시가 남긴 로그와 이어 볼 수 없음
2. 형식에 맞으면 쓰고, 아니면 요청을 거부한다 — 값이 깨끗함 / 요청을 구분하려는 값 때문에 요청이 실패함
3. 형식에 맞으면 쓰고, 아니면 버리고 새로 만든다 — 앞단과 이어 볼 수 있고 요청은 그대로 처리됨 / 보내는 쪽이 고른 값이 로그에 남음

**오류 응답에 싣는가**
1. 헤더로만 준다 — 본문이 그대로임 / 화면이 헤더를 따로 읽어야 하고, 본문만 남긴 오류 보고에는 ID가 없음
2. 헤더와 본문 둘 다 — 오류 화면이 본문만으로 보여 줄 수 있음 / 본문이 요청마다 달라짐

**다른 스레드로 어떻게 넘기는가**
1. 실행기의 장식(`TaskDecorator`)을 직접 둔다 — 코드가 한 곳에 보임 / Spring Modulith가 이벤트 실행기의 장식을 자기 것으로 바꿔 끼워서 불리지 않음
2. 문맥 전달 장치(`ContextPropagatingTaskDecorator`)에 로그 문맥을 넘길 값으로 등록한다 — Spring Modulith가 거는 것과 같은 장치라 서로 덮어써도 결과가 같음 / 그 장치가 실행기에 걸려 있어야 함

## 결정
묶는 것은 1번, 들어온 ID는 3번, 오류 응답은 2번, 넘기는 것은 2번으로 한다.

- 요청마다 ID 하나를 정한다. 헤더 이름은 요청과 응답 모두 `X-Request-Id`다.
- 들어온 ID는 영문자·숫자·`_`·`-`로 된 8~64자일 때만 쓴다. 맞지 않으면 버리고 새로 만든다(16진수 32자). 요청은 거부하지 않는다.
- ID를 정하는 필터는 모든 필터의 가장 바깥에서 돈다. 필터 단계 오류를 잡는 필터가 남기는 로그에도 ID가 찍힌다.
- 컨테이너가 오류 경로로 다시 보낸 요청은 처음에 정한 ID를 다시 쓴다.
- 모든 응답에 헤더로 싣는다. 필터 단계 오류로 응답을 비우고 다시 쓸 때도 이 헤더는 남긴다. 다른 출처의 화면이 읽을 수 있게 드러내는 헤더에 넣는다.
- 오류 응답(Problem Details)의 본문에 `requestId`로 싣는다. 헤더와 같은 값이다.
- 로그 문맥에는 요청 ID와, 로그인한 요청이면 계정 ID를 넣는다. 아이디와 이름은 넣지 않는다.
  계정 ID는 보안 필터들 가운데 로그인 정보를 읽을 수 있게 되는 바로 그 자리에서 넣는다. CSRF 검사와 인증 검사보다 앞이라,
  로그인한 사용자의 요청이 거기서 막혀도 그 로그에 계정 ID가 찍힌다. 로그인은 했는데 누구인지 알 수 없는 로그인 정보면 요청을 멈추지 않고 표시(`unknown`)를 넣는다.
- 형식에 맞지 않아 버린 ID는 길이만, 평소에는 찍히지 않는 수준(DEBUG)으로 남긴다. 값은 남기지 않는다.
- 요청이 끝나면 로그 문맥을 통째로 비운다. 스레드는 다음 요청이 다시 쓴다.
- 요청이 낸 이벤트의 리스너 스레드로 로그 문맥을 넘긴다. 로그 문맥 없이 넘긴 작업은 빈 문맥에서 돈다.
  문맥 전달 장치는 두 길로 실행기에 걸린다. Spring Modulith의 관측 구성이 켜져 있으면 그쪽이 걸고, 꺼져 있으면(`management.tracing.enabled=false`) 이 애플리케이션이 둔 빈이 걸린다. 두 경우 모두 테스트가 있다.
- 운영 로그는 JSON 한 줄로 내보낸다(Spring Boot의 구조화 로그, logstash 형식). 요청 ID와 계정 ID는 최상위 필드다.
  그 밖의 환경은 글 형식에 `[요청 ID|계정 ID]`를 더한다.
- 로그에는 요청의 경로만 남기고 쿼리 문자열은 남기지 않는다. 쿼리 문자열을 통째로 읽는 코드는 한 곳(멱등 키의 지문)뿐이고, 다른 곳에서 읽으면 테스트가 실패한다.

## 근거
- 서버가 하나이고 밖으로 나가는 호출이 없는 지금, 필요한 것은 "한 요청의 로그를 모으는 값" 하나다. 추적 도구는 이어 볼 호출이 생긴 뒤에 들여도 늦지 않고, 그때 이 ID를 추적 ID로 바꿔 끼울 자리는 한 곳이다.
- 형식을 좁히면 줄바꿈이나 긴 값으로 로그에 가짜 줄을 끼워 넣을 수 없다. 좁힌 형식 안에서 보내는 쪽이 값을 고르는 것은 로그를 찾기 어렵게 할 뿐 다른 것을 바꾸지 못한다.
- 요청을 구분하려는 값이 요청을 실패시키면 본말이 바뀐다. 그래서 틀린 값은 거부하지 않고 버린다.
- 오류를 본 사람이 알려 줄 수 있는 것은 화면에 보이는 것뿐이다. 본문에 있어야 화면이 그대로 보여 줄 수 있다.
- 로그 문맥을 통째로 비우면, 안쪽 어디에서 무엇을 넣었든 다음 요청으로 새지 않는다.
- JSON 로그는 Spring Boot에 들어 있는 기능이라 새로 들이는 것이 없다. 스택 추적도 한 줄 안에 들어가 줄 단위로 읽는 도구가 오류 하나를 여러 줄로 쪼개지 않는다.
- 쿼리 문자열에는 검색어(이름, 전화번호 뒷자리)가 실린다. "찍지 않는다"를 약속으로만 두면 로그 한 줄을 더할 때 어길 수 있다.
- 문맥 전달에 쓰는 라이브러리(`io.micrometer:context-propagation`)는 Spring Modulith를 통해 이미 들어와 있다. 등록하는 코드가 그 타입을 쓰므로 의존성에 이름만 적었고, 버전은 Spring Boot가 정한다.

## 포기한 것
- 이벤트 봉투에는 요청 ID를 싣지 않는다. 처리에 실패해 나중에 다시 보내지는 이벤트의 로그에는 요청 ID가 없다. 이벤트의 ID로 찾아야 한다.
- 멱등 키로 다시 나가는 응답은 본문이 처음 그대로다. 본문의 `requestId`는 처음 요청의 것이고 헤더는 지금 요청의 것이라 둘이 다르다. 일을 한 것은 처음 요청이므로 본문의 ID가 가리키는 로그가 맞다.
- 오류 응답의 본문이 요청마다 달라진다. 본문을 통째로 비교하는 쪽은 `requestId`를 빼고 비교해야 한다.
- 들어온 ID가 형식에 맞으면 누가 보냈는지 묻지 않고 쓴다. 같은 ID를 여러 요청에 실어 보내면 그 요청들의 로그가 한 ID로 묶인다.
- 로그인하지 않은 요청의 로그에는 계정 ID가 없다. 로그인 정보를 읽기 전에 난 오류(세션 저장소 장애 등)의 로그에도 없다.
- 서버가 요청을 필터에 넘기기 전에 거부한 응답(깨진 요청 줄, 너무 큰 헤더)에는 요청 ID가 없다.
- 형식에 맞지 않는 ID를 앞단이 계속 보내도 요청은 모두 정상으로 처리된다. 앞단의 로그와 이어지지 않는다는 것은 평소의 로그로는 드러나지 않는다.
- 쿼리 문자열 규칙이 막는 것은 "쿼리 문자열을 통째로 읽는 코드"뿐이다. 컨트롤러가 받은 검색어를 직접 찍거나 예외 문구에 값이 실리는 것은 막지 못한다.
- 요청 밖에서 남는 로그(기동, 주기 작업)에는 요청 ID가 없다.
- 요청이 끝났다는 로그(접근 로그)는 애플리케이션이 남기지 않는다. 앞단의 프록시가 남기고, 그 로그에 쿼리 문자열이 남지 않게 하는 것은 프록시 설정의 몫이다.
- 브라우저의 방문 기록에 남는 쿼리 문자열은 이것으로 막지 못한다. 검색어를 본문으로 옮겨야 한다.
- JSON 형식 자체는 자동 테스트가 없다. 테스트에서 로그 형식을 바꾸면 같이 도는 다른 테스트의 출력까지 바뀐다. 실제로 띄워 확인했다.
- 로그 문맥이 넘어가는 것은 Spring Boot가 만드는 실행기에 한한다. 실행기를 직접 만들어 쓰면 그 실행기에는 장치가 걸리지 않는다. 이벤트 리스너의 실행기를 바꾸면 테스트가 실패한다.
- 넘기는 값은 로그 문맥 전체이고, 되돌릴 때도 전체를 되돌린다. 다른 도구가 로그 문맥에 넣는 값(추적 ID 등)이 생기면 그 값까지 함께 덮는다.
- 로그에서 개인정보를 가리는 장치는 없다. 지금은 "넣지 않는다"로 지킨다.

## 재검토 조건
- 메시지 브로커를 들일 때 → 메시지 헤더로 요청 ID를 넘기고, 받는 쪽이 로그 문맥에 넣음
- 서버가 둘 이상이 되거나 밖으로 나가는 호출을 이어 봐야 할 때 → 분산 추적 도구로 바꾸고 이 ID를 추적 ID로 대체. 그 도구가 로그 문맥에 넣는 값과 여기서 통째로 넘기고 되돌리는 방식이 부딪치지 않는지 확인
- 앞단의 로그와 이 서버의 로그가 이어지지 않을 때 → 버린 ID의 수를 지표로 세어 경보
- 응답을 비동기로 쓰는 경로(실시간 전송 등)가 생길 때 → 비동기로 다시 들어온 스레드에도 로그 문맥을 채움
- 다시 보내지는 이벤트의 로그를 처음 요청과 이어 봐야 할 때 → 이벤트 봉투에 요청 ID 추가
- 같은 ID로 묶인 요청이 로그를 찾는 데 방해가 될 때 → 앞단의 프록시가 정한 값만 받고 그 밖에서 온 값은 버림
- 요청마다 걸린 시간과 결과를 애플리케이션에서 봐야 할 때 → 요청이 끝났다는 로그를 추가(경로만)
- 로그에 개인정보가 실린 것이 발견될 때 → 가리는 장치를 추가
