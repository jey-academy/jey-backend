# ADR-0031: 요청마다 세션의 계정을 확인한다

- 상태: 채택
- 날짜: 2026-10-13

## 배경
세션에는 로그인할 때의 역할과 지점이 들어 있고, 요청은 그것만 보고 처리됐다. 계정을 차단하거나 역할·지점·비밀번호를 바꾸면 그 계정의 세션을 지워서 반영했다(ADR-0019, ADR-0030).

세션을 지우는 것은 계정을 고치고 커밋한 뒤의 별도 단계다. 그 단계가 실패하면(세션 저장소 장애) 계정은 바뀌었는데 세션이 남는다.
그때는 "다시 보내라"는 전용 오류(503)로 알렸지만, 다시 보내지 않으면 남은 세션이 만료될 때까지(직원은 최대 16시간) 옛 권한으로 계속 일했다.
차단된 계정, 내려간 역할, 다시 정하기 전의 비밀번호로 로그인된 세션이 모두 해당한다.

"세션이 지금 계정과 같은 권한인가"를 보는 곳도 둘이었고 기준이 서로 달랐다(로그인 직전의 재확인은 연계 학원 식별자와 비밀번호까지, 옛 세션을 찾는 쪽은 역할과 지점만).

## 선택지
**무엇을 비교하는가**
1. 세션에 든 역할·지점을 계정과 대조한다 — 스키마가 그대로임 / 비밀번호가 바뀐 것을 알 수 없음(세션에 비밀번호의 흔적이 없다). 그 경우는 계속 세션 지우기에만 기댐
2. 계정에 판 번호를 두고, 세션에 로그인할 때의 번호를 넣어 비교한다 — 비밀번호 변경도 잡음, 기준이 숫자 하나 / 컬럼이 하나 늘고, 번호가 없는 기존 세션은 다시 로그인해야 함

**요청마다 계정을 어떻게 읽는가**
1. 매번 DB에서 읽는다 — 차단이 다음 요청에 바로 반영됨, 지울 것이 없음 / 요청마다 조회 하나
2. 짧게 기억해 둔다 — 조회가 줄어듦 / 기억하는 시간만큼 차단이 늦게 반영되고, 지우는 장치가 또 실패할 수 있음

**계정을 읽지 못했을 때(DB 장애)**
1. 통과시킨다 — DB를 쓰지 않는 요청은 계속 됨 / 그동안 차단이 조용히 풀림
2. 막는다 — 확인하지 못한 세션으로 일하지 못함 / DB를 쓰지 않는 요청도 그동안 서버 오류

**세션을 지우지 못했을 때의 전용 오류(503)**
1. 남긴다 — 관리자가 알 수 있음 / 지우지 못해도 옛 세션은 막히므로, 성공한 변경에 실패로 답하게 됨
2. 없앤다 — 변경의 성패와 응답이 맞음, 다시 보내면 지우던 복구 길도 필요 없음 / 지우지 못한 것은 서버 로그에만 남음

## 결정
비교는 2번, 읽기는 1번, 읽지 못하면 2번, 전용 오류는 2번으로 한다.

- 계정에 권한 판 번호를 둔다. 차단, 역할·지점 변경, 비밀번호 변경(관리자가 다시 정하는 것과 본인이 바꾸는 것 모두) 때 1씩 오른다.
  이름 고치기와 차단 풀기는 올리지 않는다. 번호는 계정 엔티티의 메서드 안에서 올린다.
- 로그인할 때 그 번호를 세션에 넣는다. 비밀번호를 검증하려고 계정을 읽었을 때의 번호다.
- 세션이 있는 요청마다 계정을 읽어 그 세션이 아직 유효한지 본다. 유효하려면:
  - 계정이 있고 차단되지 않았다.
  - 권한 판 번호가 세션의 것과 같다.
  - 역할, 지점, 연계 학원 식별자가 세션의 것과 같다(번호를 올리지 않고 DB를 직접 고친 경우를 잡는다).
- 이 기준은 한 곳에 둔다. 로그인 직전의 재확인도 같은 기준을 쓴다.
- 유효하지 않은 세션은 그 자리에서 끊고 요청은 계속 보낸다. 로그인이 필요한 경로면 401을 받는다. 번호가 없거나 읽을 수 없는 세션도 끊는다.
- 확인은 최대 유지 시간 확인 뒤, 로그인 정보를 읽기 전에 한다. 세션이 없는 요청은 계정을 읽지 않는다.
- 계정을 읽지 못하면 요청을 서버 오류로 끝낸다. 세션은 지우지 않는다. DB가 돌아오면 그 세션으로 계속 일한다.
- 본인이 비밀번호를 바꾸면 지금 세션에 새 번호를 넣는다(지금 세션은 남긴다는 ADR-0030의 결정은 그대로다). 다른 세션을 지우기 전에 넣는다.
- 계정을 바꾼 뒤 세션을 지우는 일은 그대로 한다. 다만 미리 치워 두는 일이라서, 지우지 못해도 변경은 성공으로 답하고 로그만 남긴다.
  세션을 지우는 쪽이 예외를 던지지 않는다(부르는 쪽마다 감싸지 않아도 되게).
  전용 오류(503)와, 다시 보내면 지우던 복구 길 둘(바뀐 것이 없는 고치기 요청이 옛 세션을 찾아 지우기, 새 비밀번호가 지금과 같은 요청이 거부되기 전에 다른 세션 지우기)을 없앤다.

## 근거
- 세션을 지우는 것만으로는 "차단하면 못 쓴다"를 지킬 수 없다. 지우는 단계가 실패할 수 있고, 실패를 알리는 것은 고치는 것이 아니다.
  요청마다 확인하면 지우기가 실패해도 다음 요청에서 막힌다.
- 비밀번호를 다시 정하는 흔한 이유는 계정이 뚫린 것 같아서다. 그때 옛 세션이 남는 것이 가장 나쁜 경우인데, 역할·지점만 대조하는 방식은 그것을 못 잡는다.
- 번호 하나로 비교하면 "무엇이 바뀌면 옛 세션을 막는가"가 번호를 올리는 곳에 모인다. 비교하는 쪽은 바뀔 일이 없다.
- 직원 수가 적고 요청마다 이미 세션 저장소를 읽고 있다. 기본 키 조회 하나는 그에 비해 작다.
  기억해 두면 지금 고치려는 문제(반영을 별도 장치에 기대는 것)가 모양만 바뀌어 다시 생긴다.
- DB가 죽으면 거의 모든 요청이 어차피 실패한다. 그 시간에 차단이 풀리는 것보다 몇 안 되는 요청이 같이 실패하는 쪽이 낫다.
  세션을 지우지 않으므로 장애가 "모두 로그아웃됐다"로 보이지 않는다.
- 차단이 저장됐고 옛 세션도 막히는데 503으로 답하면 관리자는 실패했다고 읽는다. 다시 보낼 이유도 없어졌다.
- 차단할 때 번호가 오르므로, 차단을 풀어도 차단 전의 세션은 살아나지 않는다.

## 포기한 것
- 로그인한 요청마다 DB 조회가 하나 는다.
- DB 장애 중에는 DB를 쓰지 않는 요청(내 정보, 로그아웃)도 서버 오류다. 세션 쿠키가 실려 있으면 공개 경로(상태 확인, CSRF 토큰, 로그인)도 같다.
  쿠키가 없는 요청은 계정을 읽지 않으므로 그대로 된다.
- 이 변경을 배포하면 그 전에 로그인된 세션은 번호가 없어 모두 한 번 다시 로그인해야 한다.
- 이미 처리 중이던 요청은 끝까지 간다. 확인을 지난 직후에 차단된 계정의 그 한 요청은 옛 권한으로 처리될 수 있다.
- 세션을 지우지 못한 것은 서버 로그에만 남는다. 응답과 감사 로그로는 알 수 없다. 지우지 못한 세션은 저장소에 만료까지 남는다(그 세션으로 요청이 오면 그때 지워진다).
- 막힌 세션은 로그로만 남긴다. 감사 로그에는 적지 않는다(계정을 바꾼 일은 이미 적혀 있다).
- 본인이 비밀번호를 바꾼 뒤 지금 세션에 새 번호를 넣기 전에 요청이 끊기면, 바꾼 사람의 세션도 다음 요청에서 막힌다. 새 비밀번호로 다시 로그인해야 한다.
- 지금 세션에 넣은 새 번호는 그 요청이 끝날 때 세션 저장소에 적힌다. 커밋한 뒤 그때까지의 짧은 틈(다른 세션을 지우는 동안)에
  같은 세션으로 다른 요청이 오면, 그 요청이 옛 번호를 보고 세션을 끊는다. 비밀번호 변경은 성공으로 답하지만 그때 받은 세션 쿠키로는 일할 수 없고,
  새 비밀번호로 다시 로그인해야 한다. 화면이 요청을 겹쳐 보낼 때만 생긴다. 끊은 요청의 로그에 세션의 번호와 계정의 번호가 남아 이 경우를 가릴 수 있다.
- 본인 비밀번호 변경이 커밋된 뒤 지금 세션을 저장하지 못하면(세션 저장소 장애) 요청은 서버 오류로 끝난다. 비밀번호는 바뀌어 있다.
  응답으로는 알 수 없고, 바뀌었다는 것은 서버 로그와 감사 로그에 남는다.
- 이름을 고쳐도 로그인된 화면의 이름은 다음 로그인 때 바뀐다. 요청마다 계정을 읽게 됐지만 세션의 로그인 정보를 고쳐 쓰지는 않는다.
- 번호를 올리지 않는 길로 비밀번호를 바꾸면(DB를 직접 고침) 옛 세션이 막히지 않는다. 역할·지점은 직접 고쳐도 잡힌다.

## 재검토 조건
- 요청마다의 계정 조회가 부하 테스트나 운영에서 눈에 띌 때 → 수 초 동안 기억해 두기(그 시간만큼 차단이 늦게 반영된다)
- DB 장애 때 로그아웃이나 내 정보까지 실패하는 것이 문제가 될 때 → 그 경로만 확인에서 빼기
- 비밀번호를 바꾼 직후 로그아웃됐다는 문의가 생길 때 → 커밋하기 전에 지금 세션에 다음 번호를 저장해 두고, 요청마다의 확인이 지금 번호와 다음 번호를 모두 받게 하기
- 차단됐는데 계속 들어오는 세션을 관리자가 봐야 할 때 → 막힌 세션을 감사 로그나 지표로 남기기
- 이름을 고친 것이 바로 화면에 보여야 할 때 → 요청마다 읽은 계정으로 세션의 이름을 갱신
- 계정의 종류가 늘 때(연계 학원 계정 만들기, 학부모·학생 로그인) → 소속을 바꾸는 길마다 번호를 올리는지 확인
