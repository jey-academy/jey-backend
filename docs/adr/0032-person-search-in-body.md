# ADR-0032: 사람을 가리키는 조회 조건은 본문으로 받는다

- 상태: 채택
- 날짜: 2026-10-13

## 배경
학생 목록은 이름과 전화번호 뒷자리를 쿼리 문자열로 받았다(`GET /api/v1/students?name=…&phoneLast4=…`).

주소(경로와 쿼리 문자열)는 요청을 받는 서버 밖에도 남는다. 브라우저의 방문 기록과 주소 자동 완성, 앞단 프록시의 접근 로그가 그렇다.
애플리케이션 로그에는 쿼리 문자열을 남기지 않게 막아 두었지만(ADR-0028), 브라우저와 프록시는 서버 코드로 막을 수 없다.
학생 이름과 전화번호 뒷자리가 검색할 때마다 그곳에 쌓였다.

화면 쪽은 이미 이것을 피하고 있었다. 전화번호 뒷자리 검색은 "주소에 남는다"는 이유로 쓰지 않았다. 있는 기능을 쓰지 못하고 있던 셈이다.

## 선택지
**조건을 어디로 받는가**
1. 쿼리 문자열 그대로, 프록시의 접근 로그에서 쿼리를 지우게 설정한다 — API가 그대로임 / 브라우저의 방문 기록은 남고, 프록시 설정을 빠뜨리거나 바꾸면 다시 남음
2. 본문으로 받는다(POST) — 주소에 남지 않음 / 조회인데 POST가 됨. 주소만으로 같은 검색을 다시 열 수 없고, 브라우저와 중간 서버가 응답을 기억해 두지 않음
3. 헤더로 받는다 — 주소에 남지 않고 GET 그대로임 / 헤더에 한글을 실으려면 인코딩이 필요하고, 조건이 헤더에 있는 API는 낯설며 명세로 적기 어려움

**어느 조건까지 본문으로 옮기는가**
1. 사람을 가리키는 조건(이름, 뒷자리)만 본문으로, 나머지(지점, 페이지)는 쿼리에 둔다 — 옮기는 것이 적음 / 조건이 두 곳으로 갈려 요청을 만드는 쪽과 명세가 복잡해짐
2. 조건을 모두 본문으로 받는다 — 한 곳에서 받음 / 지점과 페이지까지 주소에서 빠짐

**기존 GET 목록**
1. 두 조건만 빼고 남긴다 — 조건 없는 목록은 GET 그대로 / 목록을 받는 길이 둘이 되고, 남은 GET에 누가 조건을 다시 붙일 수 있음
2. 없앤다 — 길이 하나 / 화면을 함께 고쳐야 함

## 결정
조건은 2번(본문), 범위는 2번(모두 본문), 기존 GET은 2번(없앤다)으로 한다.

- 이름, 전화번호처럼 사람을 가리키는 조회 조건은 주소로 받지 않는다. 그런 조회는 조건을 본문으로 받는 `POST …/search`로 만든다.
- 학생 검색은 `POST /api/v1/students/search`다. 지점, 이름의 앞부분, 전화번호 뒷자리, 페이지, 크기를 모두 본문으로 받는다. 모두 선택이고, 조건이 없으면 빈 객체를 보낸다.
  - 페이지와 크기의 기본값(0, 20)은 API 명세에 `default`로 적지 않고 설명에만 적는다. `default`가 있으면 타입 생성기가 그 필드를 필수로 만들어, 빈 객체를 보내는 호출이 타입 오류가 된다.
  - 조건을 받는 본문은 모르는 필드가 있으면 거부한다(400). 조건의 이름을 잘못 적은 요청이 조건 없는 전체 목록으로 답해지지 않게 한다.
    거부할 타입에 표시를 붙인다. 표시하지 않은 요청은 지금처럼 모르는 필드를 넘긴다. 모르는 필드의 이름은 응답에 되돌려 주지 않는다.
  - 검색 경로는 쿼리 문자열이 실려 오면 거부한다(400). 예전 방식으로 부르는 코드가 오류 없이 전체 목록을 받는 일을 막고, 주소에 조건을 싣는 코드가 첫 호출에서 드러나게 한다.
- 주소로 조건을 받던 학생 목록 GET은 없앴다.
- 이 POST는 멱등 키를 받지 않는다(ADR-0027). 바꾸는 자료가 없고, 다시 보내면 다시 조회할 뿐이다. 변경 요청이 아니지만 POST이므로 CSRF 토큰은 필요하다.
- 조건을 담는 요청 타입은 글자로 바꿨을 때(로그에 그대로 찍혔을 때) 이름과 전화번호 뒷자리를 드러내지 않는다.
- 컨트롤러가 주소(경로 변수와 쿼리 파라미터)로 받는 글자 값은 허용 목록에 적힌 것뿐이어야 한다. 테스트가 모두 모아 목록과 맞춰 본다.
  새로 더하면 실패하고, 그때 그 값이 주소에 남아도 되는지 정한다. 숫자, 참·거짓, 정해진 값 가운데 하나(enum), 날짜와 시각은 보지 않는다.
  그 밖의 타입은 모두 본다: 글자뿐 아니라 글자에서 만들어지는 값 객체(전화번호 등), 목록, 쿼리 파라미터를 묶어 받는 객체.
- 감사 로그와 계정 목록은 그대로 GET이다. 받는 조건이 계정 ID, 행위 이름, 역할 같은 것이고 사람의 이름이나 전화번호가 아니다.

## 근거
- 서버가 막을 수 없는 곳에 남는 것을 줄이는 방법은 그곳으로 보내지 않는 것뿐이다. 프록시 설정으로 지우는 것은 설정이 맞을 때만 지켜지고, 브라우저의 기록은 손댈 수 없다.
- 데스크 PC는 여러 사람이 쓰고 하루 종일 켜져 있다. 방문 기록에 학생 이름이 쌓이는 것이 실제로 일어나는 자리다.
- 조건을 한 곳에서 받으면 요청을 만드는 코드도, 검증도, 명세도 한 벌이다. 지점과 페이지가 주소에서 빠져서 잃는 것은 없다(화면의 주소와 API의 주소는 따로다).
- 운영 전이라 기존 GET을 없애도 맞춰야 할 쪽이 화면 하나뿐이다. 제이G패스와 수납의 화면이 학생 검색을 쓰기 시작하면 바꾸는 값이 커진다.
- 규칙을 문서로만 두면 다음 검색을 만들 때 다시 쿼리로 받기 쉽다. GET에 조건을 붙이는 것이 가장 익숙한 방식이기 때문이다. 테스트가 그 자리에서 묻게 한다.
- 검색에서 조건이 조용히 빠지면 "틀린 결과"가 "맞는 결과"처럼 보인다. 이름으로 찾았는데 전체 목록이 나오고, 뒷자리로 찾은 후보 목록에 무관한 학생이 든다.
  쿼리 문자열일 때도 모르는 조건은 무시됐지만, 본문으로 옮기면서 조건의 이름을 손으로 적는 자리가 생겼다. 오류로 답하는 편이 안전하다.

## 포기한 것
- 조회가 POST가 됐다. 주소만으로 같은 검색 결과를 다시 열거나 남에게 건넬 수 없다. 브라우저와 중간 서버가 응답을 기억해 두지 않는다(기억해 두면 안 되는 자료이기도 하다).
- 검색할 때마다 CSRF 토큰이 필요하다. 토큰을 받지 못한 화면은 목록도 볼 수 없다.
- 요청 본문은 주소보다 덜 남을 뿐, 어디에도 안 남는 것은 아니다. 본문을 기록하는 장치(요청 본문을 남기는 프록시, 디버그 로그)를 켜면 남는다.
- 허용 목록 테스트는 타입으로 가린다. 숫자로 된 값(전화번호를 숫자 타입으로 받는 경우)은 묻지 않고 넘긴다.
  요청 객체를 받아 파라미터를 직접 읽는 코드도 잡지 못한다.
- 모르는 필드를 거부하는 것은 표시한 본문뿐이다. 다른 요청(등록, 수정)은 모르는 필드를 여전히 넘긴다.
- 본문의 값은 느슨하게 읽힌다. 숫자 자리에 `"1"`을 보내면 1로, `1.9`를 보내면 1로, 빈 문자열을 보내면 값이 없는 것으로 읽는다.
  검색만이 아니라 모든 요청이 그렇다(JSON을 읽는 도구의 기본 동작이다). 여기서는 바꾸지 않았다. 2026-10-15 ADR-0036으로 요청 본문을 명세의 타입 그대로만 읽게 조였다.
- 운영에서 웹 계층의 디버그 로그를 켜면, 검증에 걸리거나 읽지 못한 값이 예외 문구와 함께 로그에 나온다(검증을 통과한 검색어는 나오지 않는다).
  본문으로 옮겼어도 그 설정을 켜는 동안은 틀린 입력이 로그에 남는다. 켜야 할 일이 생기면 그 전에 본다.
- 허용 목록에 더할지 본문으로 옮길지는 사람이 정한다. 테스트는 묻기만 한다.
- 화면의 주소에 검색어를 두는 것은 이 결정으로 막지 못한다. 화면 쪽의 규칙이다.

## 재검토 조건
- 검색 결과를 주소로 건네야 하는 업무가 생길 때 → 검색 조건을 서버에 잠깐 저장하고 그 ID만 주소에 싣기
- 조회 POST가 늘어 변경 요청과 구분이 어려워질 때 → 조회용 경로 이름(`/search`)을 규칙으로 고정하거나 조회 전용 메서드(QUERY)가 쓸 만해졌는지 보기
- 숫자로 된 개인정보를 주소로 받는 API가 생기려 할 때 → 허용 목록 테스트가 타입이 아니라 이름으로도 보게 넓히기
- 값을 느슨하게 읽어서 틀린 조건으로 조회한 일이 생길 때(숫자 자리의 글자, 소수) → 본문의 값을 타입 그대로만 받게 조이기(모든 요청에 걸리는 설정이다). 일이 생기기 전에 ADR-0036으로 조였다
- 등록이나 수정에서 필드 이름의 오타로 값이 빠진 채 저장된 일이 생길 때 → 그 본문에도 모르는 필드 거부를 붙이거나, 모든 요청 본문으로 넓히기
- 감사 로그나 계정 목록에 이름으로 찾는 조건을 더하려 할 때 → 그 조회도 `POST …/search`로 옮기기
