# ADR-0033: 패스 사용 처리는 등록된 학생을 받아 한 트랜잭션으로 끝낸다

- 상태: 채택
- 날짜: 2026-10-15

## 배경
데스크에서 패스를 쓰면 세 가지 일이 이어진다. 패스를 쓴 것으로 표시하고, 학생을 새로 등록하고, 할인된 첫 달 수강료를 청구해 수납 기록에 남긴다.
처음에는 사용 처리 API 하나가 이 셋을 한꺼번에 하도록 구상했다.

걸리는 점이 두 가지 있었다.

- 학생 등록은 따로 커밋한다. 동시에 등록해도 학부모가 한 명만 남도록 학부모를 찾거나 만드는 일을 독립 트랜잭션으로 돌리기 때문이다(ADR-0023).
  그래서 등록과 패스 사용을 한 트랜잭션에 넣을 수 없고, 억지로 묶으면 학생은 등록됐는데 패스는 그대로인 상태가 생길 수 있다.
- 청구와 수납 기록은 수납 모듈이 맡는데, 수납 모듈은 패스보다 늦게 만든다.

패스는 신규 등록에만 쓴다. 사용 처리 때 신규 여부를 무엇으로 판단할지도 정해야 했다.

## 선택지
**사용 처리와 학생 등록**
1. API 하나가 등록까지 한다 — 화면은 한 번만 부름 / 등록이 커밋된 뒤 사용 처리가 실패하면 반쯤 끝난 상태가 남는다. 다시 보내면 등록이 "같은 이름의 학생"으로 거부되므로 재시도 경로를 따로 만들어야 함
2. 둘로 나눈다: 등록은 기존 등록 API로 하고, 사용 처리는 등록된 학생의 ID를 받는다 — 사용 처리가 한 트랜잭션으로 끝나고 등록에 붙은 보호(번호 대입 한도, 감사 기록)를 그대로 씀 / 화면이 두 번 부르고, 중간에 끊기면 등록만 된 학생이 남음
3. 사용을 예약하고, 등록한 뒤, 확정한다 — 반쯤 끝난 상태를 서버가 모두 관리함 / 예약 해제와 멈춘 예약 청소가 필요함

**본인 확인을 언제 하는가**
1. 사용 처리 때만 한다 — API가 늘지 않음 / 이름이나 번호가 패스와 다르다는 것을 학생을 등록한 뒤에야 알게 됨
2. 등록 전에 미리 맞춰 보고, 사용 처리 때 한 번 더 본다 — 등록 전에 걸러짐 / API가 하나 늘고, 아무 번호나 넣어 볼 수 있어 횟수 한도가 필요함

**신규 학생의 판단**
1. 서버가 학생 자료로 확인한다 — 잘못 쓰는 것을 서버가 막음 / 확인할 근거를 골라야 함
2. 직원 판단에 맡기고 기록만 남긴다 — 단순함 / 다니던 학생에게 쓰는 것을 막지 못함
3. 학생의 등록일이 오늘인지 본다 — 화면의 기준과 같음 / 등록일은 직원이 고칠 수 있어 확인이 되지 않음

**금액과 청구**
1. 사용 처리에서 금액을 계산하고 청구를 만든다 — 처음 구상과 같음 / 수납 모듈이 아직 없음
2. 사용 처리는 금액을 다루지 않고, 수납 모듈을 만들 때 잇는다 — 패스를 먼저 끝낼 수 있음 / 그때까지 사용 처리만으로는 수납 기록이 생기지 않음

## 결정
등록은 2번(둘로 나눈다), 본인 확인은 2번(미리 보고 한 번 더), 신규 판단은 1번(서버가 확인), 금액은 2번(수납 모듈 때 잇는다)으로 한다.

- 데스크 화면은 다음 순서로 부른다.
  1. 패스를 확인한다(QR 또는 패스 번호).
  2. 등록 폼에 적은 학생 이름과 학부모 번호로 본인 확인을 미리 한다(`POST /api/v1/dongtanpass/passes/{id}/holder-check`). 이름과 번호가 각각 맞는지 따로 답한다.
  3. 기존 등록 API로 학생을 등록한다.
  4. 받은 학생 ID로 사용 처리를 부른다(`POST /api/v1/dongtanpass/passes/{id}/redeem`). 실패하면 그 학생 ID로 사용 처리만 다시 부른다.
- 미리 확인하는 API는 번호를 마음대로 넣어 볼 수 있으므로 계정별 횟수 한도를 건다. 맞든 틀리든 한 번으로 센다. 멱등 키는 받지 않는다(바뀌는 것이 없다).
- 사용 처리는 한 트랜잭션에서 패스를 잠그고(낙관적 락), 아래를 모두 확인한 뒤 사용 기록을 저장하고 `dongtanpass.pass-redeemed` 이벤트를 낸다.
  - 패스가 발급 상태이고 기간 안이다.
  - 사용하는 지점이 이 할인을 주는 지점이다.
  - 학생이 신규다. 이 학생의 패스 사용 기록이 없고, 학생 자료를 만든 지 7일이 지나지 않았고(만든 시각 기준, 설정값), 재원 중이다. 그만뒀다가 다시 온 학생은 자료가 이미 있으므로 신규가 아니다.
  - 학생이 패스의 주인과 같다(ADR-0035). 미리 확인을 거쳤어도 여기서 다시 본다.
  - 사용하는 지점과 학생의 지점이 같고, 처리하는 직원이 그 지점 소속이다.
- 사용 기록은 패스 하나에 하나, 학생 한 명에 하나다(둘 다 유니크 키). 같은 패스를 동시에 쓰면 하나만 성공하고 나머지는 "이미 사용됨"을 받는다.
- 사용 처리는 멱등 키를 받는다(ADR-0027).
- 금액 계산, 청구, 수납 기록은 사용 처리에 넣지 않는다. 수납 모듈을 만들 때 사용 기록과 청구를 잇는 방법을 정하고, 사용 기록에 청구와 결제를 가리키는 열을 더한다.

## 근거
- 어느 길을 골라도 반쯤 끝난 상태는 생긴다. 2번에서 남는 것은 등록만 된 학생인데, 해가 없고 같은 학생 ID로 사용 처리만 다시 부르면 끝난다. 1번과 3번은 그 상태를 풀 장치를 서버에 더 둬야 한다.
- 등록에는 학부모 중복 방지, 전화번호 대입 한도, 감사 기록이 이미 붙어 있다. 사용 처리가 이것을 다시 만들 이유가 없다.
- 패스와 맞지 않는 학생이 등록까지 가면 학부모가 데스크에 선 채로 연계 학원의 재발급을 기다려야 한다. 등록 전에 맞춰 보면 그 자리에서 고칠 수 있다. 최종 판단은 사용 처리가 하므로 미리 확인을 건너뛰어도 잘못 쓰이지는 않는다.
- 등록일은 고칠 수 있어도 자료를 만든 시각은 고칠 수 없다. 그래서 데스크가 방금 등록한 학생만 통과하고 다니던 학생은 걸러진다. 7일은 다음 날 다시 시도하는 경우를 위한 여유다.
- 수납 모듈이 생기기 전에는 패스만으로 운영을 시작하지 않는다. 사용 처리가 금액을 몰라도 운영에 빈 곳이 생기지 않는다.

## 포기한 것
- 화면이 API를 세 번 부른다. 사용 처리가 실패하면 화면이 다시 시도해야 한다.
- 등록은 됐지만 패스를 쓰지 않은 학생이 남을 수 있다. 서버가 이런 학생을 따로 찾아 주지는 않는다.
- 학생 자료를 다른 곳에서 옮겨 오면 옮긴 학생도 7일 동안은 새로 만든 학생으로 보인다. 옮기는 작업에서 따로 막아야 한다.
- 학생 자료를 만들고 7일이 지나면 그 학생에게는 패스를 쓸 수 없다. 늦게 가져온 패스는 관리자가 따로 처리해야 한다.
- 수납 모듈과 이을 때까지 사용 처리와 수납 기록은 서로를 모른다.

## 재검토 조건
- 수납 모듈을 만들 때 → 사용 기록과 청구를 잇는 방법(결제 완료 이벤트를 받아 사용을 확정하는 등)을 정하고 이 결정을 고침
- 등록만 되고 쓰이지 않은 학생이 실제로 쌓일 때 → 그런 학생을 보여 주는 조회를 더하거나 3번(예약)을 다시 봄
- 7일 안에 처리하지 못하는 일이 되풀이될 때 → 기간을 늘리거나 관리자의 예외 처리를 더함
- 학생 자료를 옮겨 올 때 → 옮긴 학생이 신규 확인을 통과하지 못하게 함
- 미리 확인의 한도에 걸리는 일이 잦을 때 → 한도를 늘리거나 패스마다 세도록 바꿈
