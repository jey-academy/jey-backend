# ADR-0036: 요청 본문은 명세의 타입 그대로만 읽는다

- 상태: 채택
- 날짜: 2026-10-15

## 배경
요청 본문(JSON)의 값이 느슨하게 읽혔다. JSON을 읽는 도구(Jackson)의 기본 동작이고, 검색만이 아니라 모든 요청 본문이 그랬다.
아래 표는 이 앱의 실제 JSON 설정으로 값을 읽어 본 결과다.

| 보낸 값 | 받는 칸 | 읽힌 값 |
|---|---|---|
| `"1"`, `1.9`, `1.0` | 숫자 | 1 |
| `""` | 숫자, 날짜 | 값 없음 |
| `1`, `true` | 글자 | `"1"`, `"true"` |
| `"true"`, `1` | 참거짓 | `true` |
| `1`, `"1"` | enum | 선언 순서의 두 번째 값 |
| `20261015` | 날짜 | 57442년(날 수로 해석) |
| `[2026,10,15]` | 날짜 | 2026-10-15 |
| `"1000"` | 금액 | 1000 |
| `""` | 금액 | 서버 오류(500) |

틀린 요청이 오류 없이 다른 뜻으로 처리됐다. 지점 ID `1.7`은 지점 1이 되고, 역할 칸의 `0`은 관리자 역할이 됐다. 화면이 빈 칸을 `""`로 보내는 버그도 드러나지 않았다.
정수 범위를 넘는 숫자는 400이기는 했지만 어느 칸인지 없이 요청 형식 오류(`COMMON_BAD_REQUEST`)로 나갔다. 범위 안에서 상한을 넘은 값은 칸 이름과 함께 검증 실패(`COMMON_VALIDATION_FAILED`)로 나가서, 같은 "너무 큰 값"인데 경계에 따라 응답이 달랐다.

앞으로 동탄고 패스와 수납이 금액과 횟수를 본문으로 받는다. 금액 칸의 소수나 글자가 다른 뜻으로 읽히기 전에 정해야 했다.

## 선택지
**무엇을 막는가**
1. 명세의 타입과 다른 모양은 모두 막는다 — 규칙이 "명세의 타입 그대로" 하나 / 지금 통과하던 느슨한 요청이 모두 400이 됨
2. 뜻이 바뀌는 것만 막는다(소수→정수, 번호→enum, 숫자→날짜, 빈 문자열→값 없음) — 깨지는 요청이 적음 / 어떤 변환은 되고 어떤 것은 안 되는지를 따로 기억해야 함
3. 처음 드러난 넷만 막는다 — 변경이 가장 작음 / enum과 날짜의 느슨함이 남음

**어디에 거는가**
1. 앱 전체의 JSON 설정 하나에 건다 — 설정이 한 곳, 모든 읽기가 같은 규칙 / 저장해 둔 이벤트를 다시 읽는 곳까지 조여져, 어긋난 이벤트 하나가 되살아나지 못하고 다시 보내기마다 실패함
2. 요청 본문을 읽는 곳에만 건다 — 영향이 요청에 그침 / 설정이 둘이 됨

**범위를 넘는 숫자**
1. 칸 이름과 함께 검증 실패로 답한다 — 경계와 무관하게 같은 모양 / 오류를 바꾸는 곳이 하나 늚
2. 지금처럼 요청 형식 오류로 둔다 — 그대로 / 응답 모양이 경계에서 갈림

## 결정
막는 것은 1번(모두), 거는 곳은 2번(요청 본문만), 범위를 넘는 숫자는 1번(칸 이름과 함께)으로 한다.

- 요청 본문의 값은 API 명세에 적힌 타입 그대로만 읽는다. 아래는 막는다.
  - 숫자 칸: 문자열, 소수(`1.0` 포함), 빈 문자열
  - 글자 칸: 숫자, 참거짓
  - 참거짓 칸: 문자열, 숫자
  - enum 칸: 번호(숫자든 숫자 문자열이든), 빈 문자열
  - 날짜·시각 칸: 숫자, 배열, 빈 문자열
  - 금액 칸: 문자열, 빈 문자열
- 막지 않는 것: `null`(값 없음), 글자 칸의 빈 문자열(비울 수 없는 칸은 검증이 막는다), 금액 칸의 소수(금액 규칙이 따로 본다), 쿼리 파라미터와 경로 값(글자에서 바꾸는 것이 정상이다).
- 엄격한 설정은 앱 전체의 JSON 설정에서 파생해 만들고 HTTP 요청·응답의 변환에만 쓴다. 모듈, 값 객체의 읽기, 모르는 필드 거부는 그대로 물려받는다. 쓰기 설정은 바꾸지 않아 응답 모양은 그대로다.
- 앱 전체의 설정(이벤트 발행 기록, 감사 로그)은 바꾸지 않는다.
- 위 값과 정수 범위를 넘는 숫자는 400 `COMMON_VALIDATION_FAILED`로 답하고 `errors[].field`에 칸 이름을 싣는다(목록 안이면 `items[1].page`). 문구는 다른 형식 오류와 같은 고정 문구이고 보낸 값은 싣지 않는다(ADR-0014).
- 칸을 알 수 없는 실패(JSON이 아니거나 모양이 통째로 틀림)는 지금처럼 `COMMON_BAD_REQUEST`다.

## 근거
- 프론트의 타입은 API 명세에서 만든다. 명세의 타입 그대로 보내는 화면은 영향이 없고, 다르게 보내는 화면은 버그를 품고 있던 것이다. 규칙이 "명세 그대로" 하나면 서버와 화면이 같은 것을 기준으로 삼는다.
- 바꾸기 전에 지금 화면이 보내는 요청 본문을 모두 확인했다. 본문은 명세에서 만든 타입으로만 만들고(타입 검사를 피하는 형 변환이 없다), ID와 금액은 숫자로 바꿔 보내며, 빈 선택 칸은 값을 빼고 보낸다. 느슨한 읽기에 기대는 화면은 없었다. 그래서 이 결정으로 달라지는 것은 틀린 요청의 응답뿐이다.
- 뜻이 같은 변환(`"1"`→1)만 남겨 두면 어디까지가 같은 뜻인지를 사람이 기억해야 한다. 빈 문자열과 소수처럼 같은 뜻처럼 보이다 다른 뜻이 되는 경우가 경계에 있다.
- 저장해 둔 이벤트는 이 앱이 같은 설정으로 쓴 것이라 조일 이유가 없다. 거기서 읽기가 실패하면 그 이벤트는 다시 보내도 낫지 않는다. 막아야 할 것은 바깥에서 들어오는 값이다.
- 엄격한 설정을 따로 처음부터 만들면 값 객체와 모듈 설정이 두 곳에서 갈라진다. 앱 설정에서 파생하면 바꾸는 곳은 하나다.
- 범위를 넘는 숫자도 "그 칸의 값이 틀렸다"다. 화면이 그 칸 밑에 오류를 보여 줄 수 있어야 한다.

## 포기한 것
- 느슨한 요청은 400이 된다. 지금 화면에는 그런 곳이 없었지만, 앞으로 만드는 화면이 숫자를 글자로 보내거나 빈 칸을 `""`로 보내면 그 칸의 오류를 받는다.
- JSON 설정이 둘이 된다. 요청 쪽 설정이 앱 설정에서 파생되는지를 테스트로 묶어 둔다.
- 날짜의 배열 형식을 막으려고 날짜 읽기를 얇게 감싼다. 감싼 쪽은 Jackson의 날짜 읽기가 바뀔 때 함께 봐야 한다.
- 이 앱이 아닌 곳에서 넣은 이벤트나 저장값은 여전히 느슨하게 읽힌다.

## 재검토 조건
- 외부 시스템(연계 학원 시스템 등)이 이 API를 부르게 될 때 → 그쪽이 보내는 형식을 확인하고, 받아 줄 변환이 있으면 그 경로에만 연다
- 저장해 둔 값이나 이벤트를 바깥에서 넣는 경로가 생길 때 → 그 읽기에도 엄격한 설정을 건다
- 금액 칸에 소수를 받지 않게 정할 때 → 금액의 읽기 규칙과 함께 정한다
