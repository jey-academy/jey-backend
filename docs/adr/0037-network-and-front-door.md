# ADR-0037: 앞단은 CloudFront 하나로 두고, 앱 서버·DB·Redis는 사설 서브넷에 둔다

- 상태: 채택
- 날짜: 2026-10-18

## 배경
운영 서버는 한 대다. 학부모 전화번호 같은 개인정보를 다루므로 데이터 저장소는 인터넷에서 직접 닿지 않아야 한다. 앱 서버도 사설 서브넷에 두는 것이 흔한 구조다. 보안 그룹을 실수로 넓게 열어도 바깥에서 닿지 않기 때문이다.

흔한 앞단은 로드 밸런서(ALB)다. 다만 서버가 한 대라 로드 밸런서의 핵심인 트래픽 분산을 쓰지 않는데, 사용량과 관계없이 월 고정비가 든다. 사설 서브넷의 서버가 바깥(이미지 저장소, 외부 API, 관리 에이전트)에 연결하려면 NAT도 필요하다. 관리형 NAT Gateway도 월 고정비가 있다.

프론트(React 빌드)도 어딘가에서 내줘야 한다. 로그인은 서버 세션과 CSRF 쿠키를 쓴다(ADR-0019).

## 선택지
**앞단**
1. ALB + 사설 서브넷의 앱 서버 — 흔한 구조, 대상 그룹으로 무중단 배포 / 서버 한 대에 월 고정비, 분산할 대상이 없음
2. 로드 밸런서 없이 앱 서버를 공개 서브넷에 두고 Nginx가 TLS를 처리(Let's Encrypt) — 가장 쌈 / 앱 서버가 공개 서브넷에 남고, 인증서 갱신을 직접 관리
3. CloudFront VPC 오리진으로 사설 서브넷의 앱 서버에 연결 — 앱 서버가 사설 서브넷에 있고 추가 요금이 없음, 인증서는 ACM이 갱신, 웹 방화벽을 붙일 자리가 있음 / API 요청도 CDN을 지나므로 캐시를 끄고 쿠키·헤더를 넘기는 설정이 필요, 원래 프로토콜을 앱에 전달하는 헤더를 따로 다뤄야 함

**사설 서브넷의 바깥 연결**
1. NAT Gateway — 관리형, 가용성 / 월 고정비
2. NAT 인스턴스(가장 작은 ARM 인스턴스) — 비용이 아주 작음 / OS 패치를 직접 하고, AZ 하나에만 있음
3. VPC 엔드포인트만 — 바깥 경로가 없음 / 필요한 서비스마다 엔드포인트 비용이 들고, AWS가 아닌 곳(이미지 저장소, 외부 API)은 닿지 못함

**Redis**
1. 앱 서버 안의 컨테이너 — 추가 비용 없음 / 앱 서버와 메모리를 나눠 쓰고, 서버를 다시 만들면 자료가 함께 사라짐
2. ElastiCache(Valkey 엔진) — 관리형, 사설 서브넷, 전송·저장 암호화 / 월 비용이 늘고 앱에 TLS 설정이 필요

**프론트**
1. 앱 서버의 Nginx — 추가 비용 없음 / 앱 서버가 프론트도 내줘야 함
2. S3 + CloudFront(OAC, 버킷 비공개), API와 같은 주소 — 비용이 아주 작고 앱 서버와 분리됨 / 배포마다 캐시 무효화
3. 외부 정적 호스팅 — 쉬움 / 무료 플랜의 상업 이용 제한, 주소가 갈리면 쿠키 설정이 복잡해짐

## 결정
앞단은 3번(CloudFront VPC 오리진), 바깥 연결은 2번(NAT 인스턴스), Redis는 2번(ElastiCache Valkey), 프론트는 2번(S3 + CloudFront, 같은 주소)으로 한다.

- VPC 하나에 AZ 2개, 공개 서브넷 2개와 사설 서브넷 2개를 둔다. 공개 서브넷에는 NAT 인스턴스만 둔다.
- 앱 서버, RDS MySQL, ElastiCache는 사설 서브넷에 두고 공인 IP를 붙이지 않는다.
- CloudFront 배포 하나가 `/`는 S3로, `/api/*`는 VPC 오리진으로 앱 서버에 보낸다. `/api/*`는 캐시를 끄고 쿠키·헤더·쿼리를 모두 넘긴다.
- 보안 그룹은 사슬로 묶는다. 앱 서버는 CloudFront VPC 오리진에서 오는 것만 받는다. DB와 Redis는 앱 서버의 보안 그룹에서 오는 것만 받는다.
- 앱 서버 안의 Nginx는 TLS를 다루지 않는다. 무중단 배포 때 트래픽을 옮기는 데 쓴다.
- 서버 접속은 SSM Session Manager로만 한다. SSH 포트와 키 페어는 두지 않는다.

## 근거
- 지켜야 할 것은 개인정보가 든 DB이고, 그 앞의 앱 서버도 사설 서브넷에 있어야 한 겹이 더 생긴다. 3번은 1번과 같은 망 구조를 로드 밸런서의 고정비 없이 만든다.
- 2번은 더 싸지만 앱 서버가 공개 서브넷에 남는다. 그 차이가 비용 차이보다 크다고 보았다.
- 서버가 한 대인 동안 로드 밸런서가 주는 것은 관리형 인증서 정도이고, CloudFront도 그것을 준다.
- 웹 방화벽이 필요해지면 CloudFront에 붙이면 된다. 로드 밸런서를 들일 이유가 되지 않는다.
- 프론트와 API가 같은 주소라 세션·CSRF 쿠키를 상위 도메인에 걸 필요가 없고 CORS 허용 출처도 하나다.
- Redis에는 로그인 세션, 계정별 횟수 한도, 멱등 키, QR 재사용 방지 기록이 있다. 앱 서버 안에 두면 무중단 배포 중 앱 두 개와 메모리를 나눠 쓰고, 서버를 다시 만들 때 이 기록이 함께 사라진다.
- 바깥 연결의 양은 이미지 내려받기와 외부 API 호출 정도라 작다. 그 양에 NAT Gateway의 고정비는 맞지 않는다.

## 포기한 것
- CloudFront에서 앱 서버로 가는 구간은 VPC 안의 HTTP다. 이 구간을 들여다보려면 VPC 안에 있어야 한다. 받아들인다.
- NAT 인스턴스는 OS 패치를 직접 하고, 패치하며 재부팅하는 동안 앱 서버의 바깥 연결이 끊긴다. AZ 하나에만 있어 그 AZ가 멈추면 바깥 연결도 멈춘다(앱 서버도 같은 AZ의 한 대다).
- 로드 밸런서의 대상 그룹 전환과 상태 확인을 쓰지 못한다. 무중단 배포는 서버 안의 Nginx 전환으로 한다.
- API 요청도 CDN을 지나므로, 원래 프로토콜과 클라이언트 IP를 앱에 전달하는 헤더 설정을 따로 한다.
- 앱 서버 안에 Redis를 두는 것보다 월 비용이 든다.

## 재검토 조건
- 앱 서버가 두 대 이상이 될 때, 또는 배포 중 다운타임을 더 줄여야 할 때 → CloudFront 뒤에 ALB를 둔다
- 바깥 연결의 양이나 가용성 요구가 커질 때 → NAT Gateway
- 악성 요청이나 요청 폭주를 막아야 할 때 → CloudFront에 웹 방화벽
- CloudFront를 지나는 것이 API에 맞지 않는 제약(요청 크기, 시간 제한)이 생길 때 → 앞단을 다시 고른다
