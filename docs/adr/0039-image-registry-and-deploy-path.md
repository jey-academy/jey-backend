# ADR-0039: 이미지는 ECR에 두고, 배포는 OIDC와 태그 하나만 받는 SSM 문서로 한다

- 상태: 채택
- 날짜: 2026-10-19
- 개정: 2026-10-20 — 머지가 아니라 릴리스 태그로 배포한다

## 배경
운영 서버는 사설 서브넷의 EC2 한 대이고, 앞단은 CloudFront VPC 오리진이다(ADR-0037). 배포를 시작하면 사람 손 없이 새 버전이 올라가야 하고, 실패하면 이전 버전이 그대로 남아야 한다.

(개정) 처음에는 `main`에 머지할 때마다 배포했다. 주석만 고친 변경도, 화면이 아직 없는 기능도 머지하는 대로 운영에 올라갔다. 여러 변경을 모아 정한 때에 내보내고, 운영에 무엇이 올라가 있는지를 한 이름으로 가리킬 방법이 필요했다.

이를 위해 정할 것이 셋이다. 이미지를 어디에 둘지, CI가 AWS에 어떻게 인증하고 서버에 배포를 어떻게 시킬지, 무엇을 올리지 않을지다. 서버에는 SSH 포트와 키 페어가 없고 접속은 SSM으로만 한다.

## 선택지
**이미지 저장소**
1. GHCR(저장소 옆) — 설정이 가장 적음 / 비공개 패키지면 서버가 받을 때 GitHub 토큰이 필요해 그 토큰을 보관·교체해야 하고, 공개 패키지면 이미지가 바깥에 보임
2. Docker Hub — 흔함 / 1번과 같은 토큰 문제, 받기 횟수 제한
3. ECR — 서버는 인스턴스 역할로 받음(보관할 토큰이 없음), 계층은 S3 게이트웨이 엔드포인트로 받음, 태그 덮어쓰기 금지 / AWS에 묶이고 저장량만큼 비용(작음)
4. 서버에서 직접 빌드 — 저장소가 필요 없음 / 서버 메모리를 빌드가 씀, "어떤 이미지가 돌고 있나"를 추적하기 어려움

**실행과 배포**
1. ECS(Fargate 또는 EC2) — 관리형 배포·상태 확인 / 무중단 전환을 보통 ALB 대상 그룹으로 하므로 ADR-0037에서 뺀 ALB 고정비가 다시 생김
2. CodeDeploy(EC2) — AWS의 배포 제품, 배포 이력 / 한 서버 안의 blue/green은 결국 훅 스크립트로 직접 써야 해서 에이전트와 산출물 저장소만 늘어남
3. SSM Run Command로 `AWS-RunShellScript`를 보냄 — 가장 쉬움 / CI의 역할이 서버에서 root로 아무 명령이나 돌릴 수 있음
4. SSM Run Command로, 이미지 태그 하나만 받는 전용 문서를 보냄 — CI의 역할이 할 수 있는 일이 "이 저장소의 이미지로 배포" 하나로 줄어듦 / 서버의 배포 스크립트를 따로 관리해야 함

**CI의 AWS 인증**
1. 장기 액세스 키를 저장소 비밀값에 둠 — 쉬움 / 키가 새면 교체 전까지 계속 쓸 수 있음
2. OIDC로 짧은 자격 증명 — 장기 키가 없음, 신뢰 조건으로 어느 저장소·어느 환경인지 묶음 / 신뢰 정책을 정확히 써야 함

## 결정
이미지는 3번(ECR), 배포는 4번(태그 하나만 받는 SSM 문서), 인증은 2번(OIDC)으로 한다.

- 이미지 태그는 커밋 SHA다. 저장소는 태그 덮어쓰기를 막는다. 오래된 이미지는 수명 주기 규칙으로 지운다.
- 같은 커밋을 다시 배포하면(실패한 배포 다시 돌리기) 이미지를 새로 만들어 올리지 않고 이미 올린 이미지를 쓴다. 다시 만든 이미지는 바이트가 달라 같은 태그로 올릴 수 없고, 처음 올린 이미지가 검사를 지난 그 이미지다.
- 이미지에 고칠 수 있는 치명적(CRITICAL) 취약점이 있으면 올리지 않는다. CI가 이미지를 만든 뒤 AWS에 닿기 전에 검사한다. 저장소의 기본 스캔은 기록만 하고 막지 않는다.
- (개정) 배포는 릴리스 태그(`v*`, 예: `v1.0.1`)를 붙일 때 그 커밋으로 한다. `main`에 머지하면 시험만 돈다. 태그를 붙이는 것이 "지금 `main`을 내보낸다"는 결정이고, 운영의 버전은 태그 이름으로 가리킨다. 실패한 배포를 다시 돌리거나 이전 버전으로 되돌릴 때는 그 태그로 워크플로를 수동 실행한다.
- CI는 GitHub 환경 `production`에서만 역할을 맡는다(신뢰 조건이 환경). 환경은 `v*` 태그만 허용하고, 워크플로의 배포 잡도 `v*` 태그에서만 돈다(둘 중 하나가 풀려도 다른 쪽이 막는다). 신뢰 조건의 대상은 조직·저장소의 이름에 ID가 붙은 형식이다 — 같은 이름으로 다시 만든 저장소는 역할을 맡지 못한다.
- 백엔드 CI의 역할이 바꿀 수 있는 것은 이 저장소에 이미지를 올리는 것과 배포 문서를 앱 서버 한 대에 보내는 것뿐이다(그 밖에는 이미지·명령 결과 읽기와 명령 취소). 문서는 SHA 형식(`^[0-9a-f]{40}$`)의 태그 하나만 받는다. 명령은 짧은 전달 제한을 두어, 서버가 늦게 받은 옛 배포가 나중에 실행되지 않게 한다.
- 배포 스크립트의 출력(공개될 수 있는 CI 로그에 실린다)에는 앱 로그를 싣지 않는다. 실패한 슬롯의 로그는 서버 파일로 남긴다.
- 서버의 배포 스크립트가 비밀값을 Parameter Store에서 읽어 런타임 파일로 만들고, 쉬는 슬롯을 띄워 readiness를 기다린 뒤 Nginx를 옮긴다. readiness는 DB와 Redis에 닿아야 통과한다. 통과하지 못하면 옮기지 않는다.
- 프론트 CI도 같은 방식으로 자기 역할을 맡는다(프론트 버킷 쓰기와 캐시 무효화만).

## 근거
- 서버가 보관해야 하는 비밀이 하나 줄어든다. 인스턴스 역할은 이미 있고, 받기 권한만 더하면 된다.
- 태그 덮어쓰기를 막으면 "지금 도는 이미지 = 그 커밋"이 성립하고, 되돌리기는 이전 SHA로 배포 문서를 다시 보내는 것이다.
- CI가 뚫렸을 때 할 수 있는 일이 범위다. 전용 문서는 서버에서 임의의 명령을 실행하는 길을 막는다. 남는 위험은 "저장소의 이미지로 배포"이고, 그 이미지는 리뷰와 테스트를 지난 코드에서 나온다.
- 서버가 한 대인 동안 ECS나 CodeDeploy가 더해 주는 것(대상 그룹 전환, 배포 이력 화면)보다 늘어나는 것(ALB 고정비, 에이전트, 산출물 저장소)이 크다. 무중단 전환의 원리(readiness를 통과해야 옮기고, 실패하면 이전 버전 유지)는 같다.

## 포기한 것
- (개정) `main`과 운영이 잠시 다를 수 있다. 머지한 변경은 태그를 붙여야 운영에 들어간다. `main`은 언제 태그를 붙여도 되는 상태로 둔다(마이그레이션은 확장만, 화면이 없는 기능은 쓸 수 없을 뿐 깨지지 않게).
- (개정) 개발용 브랜치(develop)를 두고 모았다가 내보내는 방식은 쓰지 않는다. 서버가 한 대라 그 브랜치를 돌려 볼 환경이 없고, PR이 두 번씩 생긴다.
- GHCR이 저장소 옆에 있는 편리함. 이미지 저장소가 코드와 다른 곳에 있다.
- 배포 문서는 서버에서 root로 돈다. 문서가 받는 값은 SHA 형식으로만 제한한다.
- 서버의 배포 스크립트와 compose 파일은 손으로 설치한다. 저장소의 파일과 서버의 파일이 달라질 수 있다(구성 드리프트). 코드로 관리하는 것은 Terraform으로 옮길 때 한다(ADR-0038).
- 관리형 배포 이력 화면이 없다. 배포 기록은 GitHub 환경의 배포 이력과 SSM 명령 기록으로 본다.

## 재검토 조건
- 앱 서버가 두 대 이상이 될 때 → ALB 뒤의 ECS 또는 CodeDeploy
- Terraform으로 옮길 때 → 서버 파일의 설치를 코드로(이미지에 넣거나 배포 때 받기)
- 이미지 검사에 막히는 일이 잦아질 때 → 기준(심각도, 고칠 수 없는 취약점)을 다시 정한다
