# ADR-0046: 업무 오류의 본문에는 ID만 덧붙인다

- 상태: 채택
- 날짜: 2026-10-21

## 배경
오류 응답은 RFC 9457 Problem Details다(ADR-0014). 본문에는 `code`와 `requestId`가 있다. 화면이 오류 뒤에 이어 갈 행동에 필요한 값이 생겼다. 예: "그 달 청구가 이미 있다"(409)를 받으면 그 청구를 바로 열고 싶다.

RFC 9457은 확장 칸을 허용한다. 정할 것은 무엇을 실을 수 있게 하는지다. 이 프로젝트는 이름·전화번호를 응답·로그·예외 문구에 싣지 않는 규칙이 강하다(ADR-0009, ADR-0026).

## 선택지
1. 아무 값이나 싣는 맵(문자열·숫자) — 쓸모가 넓다 / 개인정보를 실을 자리가 생기고, 무엇이 실렸는지 코드를 봐야 안다
2. ID만(이름은 `…Id`, 값은 숫자) — 개인정보를 실을 수 없다 / 숫자가 아닌 값이 필요해지면 넓혀야 한다
3. 확장 칸 없이 `Location` 헤더 — HTTP다운 방식이다 / 멱등 키로 다시 나가는 응답은 상태와 본문뿐이라 헤더가 빠진다(ADR-0027)
4. 덧붙이지 않고 화면이 다시 조회 — 서버가 바뀌지 않는다 / 요청이 하나 늘고 화면마다 조회 코드가 생긴다

## 결정
2번으로 한다.

- `BusinessException#withId(이름, 숫자)`. 이름은 소문자로 시작하고 `Id`로 끝나는 camelCase다. 본문의 다른 칸(`requestId`)과 같은 이름, 같은 이름 두 번은 코드의 버그로 막는다.
- 변환기가 본문의 확장 칸으로 싣는다. 멱등 키로 다시 나가는 응답에도 그대로 있다.
- 권한 확인을 지난 뒤의 오류에만, 그 자료가 확인한 범위 안에 있을 때만 싣는다. ID를 받는 사람은 그 자료를 볼 수 있는 사람이다.
- 처음 쓰는 곳: 409 `BILLING_INVOICE_ALREADY_EXISTS`·`DONGTANPASS_REDEMPTION_ALREADY_INVOICED`의 `invoiceId`. 청구는 저장하기 전에 그 학생·그 달의 열린 청구를 찾아 싣는다. 그 확인을 동시에 지난 요청이 유니크 키에 걸리면 ID 없이 나간다(오류가 난 영속성 세션으로 다시 읽지 않는다). 청구는 만들 때의 학생 지점에 속하고 권한은 학생의 지금 지점으로 확인하므로, 학생이 지점을 옮겨 두 지점이 다르면 ID 없이 나간다(요청한 사람이 열 수 없는 청구로 보내지 않는다).

## 근거
- 오류 뒤의 다음 행동에 필요한 것은 대개 "어느 자료인가"다. ID면 충분하다.
- 실을 수 있는 모양을 좁혀 두면 개인정보가 오류 본문으로 새는 길이 처음부터 없다.

## 포기한 것
- 확장 칸은 공통 오류 스키마라 API 명세에 경로별 타입으로 드러나지 않는다. 그 경로의 설명에 적는다.
- 동시 요청이 겹친 드문 409와, 학생이 지점을 옮긴 뒤의 409에는 ID가 없다(두 지점을 다 다루는 관리자에게도 — 확인한 것은 학생의 지금 지점이다). 화면은 그 달 청구 목록으로 안내한다.

## 재검토 조건
- 숫자가 아닌 값(예: 문제가 된 칸의 이름)이 필요해질 때 → 허용하는 모양을 하나씩 더한다(자유 문자열은 열지 않는다)
