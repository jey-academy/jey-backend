# ADR-0050: 학생 수정은 화면이 받은 버전으로 낡은 저장을 막는다

- 상태: 채택
- 날짜: 2026-11-21

## 배경
학생 정보 수정(`PUT /students/{id}`)은 전화번호를 뺀 값을 통째로 바꾼다. 두 직원이 같은 학생 화면을 열어 두고 한 사람은 반을, 다른 사람은 학교를 고치면, 나중에 저장한 쪽이 화면에 남아 있던 옛 반을 다시 써서 앞사람의 변경을 되돌린다. 두 요청 모두 성공으로 답하고 아무도 알지 못한다.

서버는 학생을 고칠 때 학생 행을 잠근다(연락처를 세고 지우는 확인이 동시 요청에 뚫리지 않게). 그러나 잠금은 두 저장을 줄 세울 뿐이다. 뒤에 선 저장은 잠금을 얻은 뒤 낡은 화면의 값을 정상 값처럼 쓴다. 시간 차가 몇 분이어도 같은 일이 일어나므로, 이 문제의 원인은 동시에 온 요청이 아니라 낡은 화면이다.

정할 것은 셋이다. 화면이 본 상태를 어떻게 알려 줄지, 서버가 무엇과 비교할지, 어떤 변경이 그 상태를 바꾼 것으로 칠지.

## 선택지
**화면이 본 상태를 알려 주는 방법**
1. 응답과 수정 요청의 본문에 버전 칸을 둔다 — 다른 요청 칸과 같은 방식으로 읽고 검증한다 / 본문 모양이 바뀐다
2. 응답 헤더 `ETag`와 요청 헤더 `If-Match`(HTTP 조건부 요청) — 표준이다 / 같은 키로 다시 보낸 요청에 처음 응답을 다시 줄 때 상태와 본문만 다시 보내므로(ADR-0027) 응답 헤더에 뜻을 실을 수 없다
3. 아무것도 하지 않는다(마지막 저장 우선) — 바뀌는 것이 없다 / 변경이 조용히 사라진다
4. 바뀐 칸만 보내는 부분 수정(PATCH) — 서로 다른 칸을 고친 두 저장은 둘 다 남는다 / 같은 칸을 고친 두 저장은 여전히 뒤가 이긴다. 화면이 바뀐 칸을 가려 보내야 하고, "비운다"와 "그대로 둔다"를 구분할 표기가 필요하다

**서버가 비교할 것**
1. 학생에 버전 칸을 두고(JPA `@Version`), 학생 행을 잠근 뒤 요청의 버전과 비교한다
2. 마지막으로 고친 시각을 버전처럼 쓴다 — 칸을 새로 만들지 않아도 된다 / 시각의 단위와 같은 시각의 두 변경에 기대게 된다

**버전을 올리는 변경**
1. 학생 행이 바뀌는 변경만(정보 수정, 번호 바꾸기·지우기)
2. 학부모 추가·끊기·관계 바꾸기까지

## 결정
알려 주는 방법은 1번(본문 칸), 비교는 1번, 올리는 변경은 1번으로 한다.

- 학생에 버전을 둔다. 있는 학생은 0에서 시작하고, 학생 행이 바뀔 때마다 하나씩 오른다(JPA가 올린다).
- 학생 응답에 버전을 싣는다. 수정 요청은 화면이 받은 버전을 다시 보내야 한다(빠지면 400).
- 서버는 학생 행을 잠가 읽은 바로 뒤, 다른 확인보다 먼저 요청의 버전과 비교한다. 다르면 고치지 않고 409로 답한다. 화면은 다시 불러오라고 안내한다. 낡은 화면의 값으로 지점·반 같은 다른 오류를 먼저 내지 않는다.
- 바뀐 값이 없는 저장은 버전을 올리지 않는다(같은 화면에서 저장을 두 번 눌러도 거부되지 않는다).
- 학부모 연결의 변경은 버전을 올리지 않는다.
- 학생 행 잠금은 그대로 둔다.
- 이 거부는 감사 로그에 남기지 않는다. 번호나 다른 자료의 존재를 드러내지 않는 업무 거부다.

## 근거
- 버전 칸만 두어서는 막히지 않는다. 서버는 요청마다 최신 행을 읽으므로, 서버 안에서 비교하면 버전이 늘 맞는다. 화면이 받은 버전을 요청에 실어 와야 낡은 화면을 알아볼 수 있다.
- 잠금과 버전은 맡는 일이 다르다. 잠금은 같은 학생을 고치는 요청을 한 줄로 세워 서버 안의 확인(남은 연락처 세기)이 뚫리지 않게 하고, 버전은 줄의 뒤에 선 저장이 낡은 화면에서 왔는지 가린다. 잠근 뒤에 비교하므로 정말 동시에 온 같은 버전의 저장도 하나만 반영된다(시험: 같은 버전으로 동시에 보낸 8건 중 1건만 성공, 7건은 409).
- 본문 칸은 다른 요청 칸과 같은 엄격한 읽기(ADR-0036)와 필수 검증을 그대로 받는다. 헤더는 다시 보내는 응답에 실리지 않는다.
- 학부모 연결은 수정 요청이 덮어쓰는 칸이 아니라 두 변경이 충돌하지 않는다. 버전을 올리면 학부모를 붙인 뒤 열어 둔 수정 화면이 이유 없이 거부된다.
- 시각보다 정수 버전이 비교가 분명하고, JPA가 바뀔 때만 올려 준다.

## 포기한 것
- 거부된 직원은 다시 불러온 뒤 입력을 다시 해야 한다. 칸 단위로 합쳐 주지 않는다.
- 학부모 정보 수정(이름 통째로 바꾸기)에는 아직 같은 문제가 있다. 같은 방식으로 따로 다룬다.
- 버전을 보내지 않는 옛 화면은 수정할 수 없다(400). 화면과 함께 바꾼다.

## 재검토 조건
- 같은 학생을 자주 동시에 고치게 되어 거부가 잦을 때 → 바뀐 칸만 비교해 겹치지 않으면 합치는 방식
- 다른 통째로 바꾸는 수정에 같은 문제가 드러날 때 → 같은 방식(본문 버전, 잠근 뒤 비교)을 쓴다
