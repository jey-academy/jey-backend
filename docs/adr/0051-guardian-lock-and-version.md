# ADR-0051: 학부모 수정은 행을 잠가 읽고, 화면이 받은 버전으로 낡은 저장을 막는다

- 상태: 채택
- 날짜: 2026-11-22

## 배경
학부모 수정(`PUT /guardians/{id}`)은 이름을 통째로 바꾸고, 번호는 보낸 경우에만 바꾼다. 이 수정에서 변경이 조용히 사라지는 경우가 두 가지 있었다.

| | 낡은 화면 | 서버 안의 끼어들기 |
|---|---|---|
| 장면 | A가 이름을 바꾼 뒤, 같은 화면을 연 B가 번호만 바꿔 저장 | A는 이름만, B는 번호만 바꾸는 두 요청이 거의 동시에 들어옴. 둘 다 최신 화면 |
| 결과 | A의 새 이름이 옛 이름으로 돌아감 | A가 건드리지 않은 번호가 옛 번호로 돌아감 |
| 원인 | 요청에 어느 시점의 화면을 보고 고쳤는지가 없음(학생 수정과 같은 문제, ADR-0050) | 학부모를 잠그지 않고 읽음. 다른 요청이 커밋하기 전의 값을 읽은 뒤, 저장할 때 모든 칸을 다시 씀 |

끼어들기는 두 요청을 무작위로 동시에 보내는 시험(20회)에서 한 번도 나오지 않았다. 번호를 바꾸는 요청이 암호화와 횟수 확인 때문에 늘 늦게 끝나 틈이 맞지 않았다. 두 트랜잭션의 순서를 고정하자(읽기 → 다른 쪽이 번호를 바꿔 커밋 → 이름만 저장) 매번 번호가 옛 값으로 돌아갔다.

## 선택지
1. 행 잠금 + 화면이 받은 버전 비교(학생 수정과 같은 방식) — 두 문제를 모두 막음, 모듈 안의 수정이 한 방식 / 같은 학부모의 수정이 줄을 섬
2. 잠그지 않는 낙관적 잠금: 버전 비교 + JPA 버전 충돌 예외를 같은 409로 변환 — 기다림이 없음 / 충돌 예외로 끝나는 길이 하나 더 생기고, 그 길을 시험하려면 틈을 맞춰야 함
3. 바뀐 칸만 UPDATE(Hibernate `@DynamicUpdate`) — 칸이 겹치지 않는 끼어들기는 막음 / 같은 칸을 고친 끼어들기와 낡은 화면은 그대로
4. Redis 분산 락 — 서버가 여러 대여도 줄을 세움 / 아래 근거

## 결정
1번으로 한다(ADR-0050과 같은 방식).

- 학부모 수정은 학부모 행을 잠가 읽는다(`SELECT … FOR UPDATE`).
- 학부모에 버전을 둔다. 이름·번호가 실제로 바뀔 때만 오른다(거부된 수정, 같은 값 재저장, 기존 학부모를 다른 학생에 연결할 때는 그대로).
- 학생 상세의 학부모 목록과 학부모 수정 응답에 버전을 싣는다. 형제의 화면에서도 같은 학부모의 버전은 하나다.
- 학부모 수정 요청은 화면이 받은 버전을 다시 보내야 한다(빠지면 400).
- 잠근 직후, 번호 중복 확인보다 먼저 버전을 비교한다. 다르면 고치지 않고 409로 답한다.
- 버전 거부는 "그 번호가 이미 있다"를 드러내지 않으므로 번호 탐색 횟수에 들지 않고 감사 로그의 거부 기록 대상도 아니다.
- 저장은 됐는데 응답만 놓친 화면의 재전송은 멱등 키로 알아본다(ADR-0027). 같은 키면 처음의 응답이 다시 가고, 버전 거부를 받지 않는다.

## 근거
- 잠금과 버전은 맡는 일이 다르다. 잠금은 서버 안의 끼어들기(먼저 읽고 나중에 덮어쓰기)를 막고, 버전은 줄의 뒤에 선 저장이 낡은 화면에서 왔는지 가린다.
- 버전이 있어도 잠금은 필요하다. 잠그지 않으면 늦은 요청이 커밋 전의 버전을 읽어 비교를 통과하고, 저장할 때 JPA의 버전 확인에 걸려 처리하지 못한 예외(500)로 끝난다(시험: 잠금을 뺐을 때 순서를 고정한 시험이 `ObjectOptimisticLockingFailureException`으로 실패).
- 버전 비교를 번호 중복 확인보다 먼저 하지 않으면, 낡은 화면으로 보낸 요청이 다른 학부모의 번호인지 알아낼 수 있었다(시험: 고치기 전 낡은 버전 + 다른 학부모 번호 → 번호 중복 응답).
- 2번은 같은 결과를 내지만 충돌 예외 길을 결정적으로 시험하기 어렵고, 학생과 학부모가 서로 다른 방식이 된다. 직원 몇 명 규모에서 잠금 대기는 의미 있는 비용이 아니다.
- 4번이 맞지 않는 이유
  - 낡은 화면은 막지 못한다. 분산 락도 동시에 들어온 요청을 줄 세울 뿐이라 몇 분 전에 연 화면의 저장은 그대로 통과한다. 버전은 어차피 필요하다.
  - 트랜잭션 밖에 있다. 락의 만료가 트랜잭션보다 먼저 오거나, 락을 푼 뒤 커밋이 늦게 끝나면 막으려던 끼어들기가 다시 생긴다.
  - 장애 지점이 하나 는다. Redis가 멈추면 학부모 수정이 모두 실패한다.
  - 지킬 대상이 DB 행 하나이고 서버도 한 대다. 같은 DB의 행 잠금이 읽기부터 커밋까지를 정확히 묶는다(ADR-0008에서 측정한 결론과 같다).

## 포기한 것
- 같은 학부모의 수정은 한 줄로 처리된다(잠금 대기).
- 거부된 직원은 다시 불러온 뒤 입력을 다시 해야 한다.
- 버전을 보내지 않는 옛 화면은 학부모를 고칠 수 없다(400). 응답에 버전을 먼저 싣고 화면이 보낸 뒤에 거부를 배포한다.

## 재검토 조건
- 서버를 여러 대로 늘리면서 DB 밖의 자원(외부 발송, 파일 등)을 한 번만 처리하도록 묶어야 할 때 → 분산 락이나 멱등 키를 그 기능에서 검토
- 같은 학부모를 자주 동시에 고치게 되어 거부가 잦을 때 → 칸 단위 병합
